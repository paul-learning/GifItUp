## Scope
The whole repository at the commit above, read against `docs/security/threat-model.md`, ADR-0009 to ADR-0014, `docs/review-lessons.md` and the M0 report. M1 covers:
- **Server:** accounts, device authentication and sessions (`server/.../auth/`), invites (`invites/`, `db/InviteRepository.kt`), the KeyPackage directory (`keypackages/`, `:keypackage`), the member list (`members/`), the database roles and migrations, HTTP limits, error handling and logging.
- **`crypto/`:** identity and KeyPackage inspection, `sign_auth`, the snapshot format, the emoji fingerprint and its table, both bindings.
- **Client:** `shared/` (auth, registration, session holder, API client, origin setting, contact book and store, claim, member list, Friends state holder), `mls/` storage (Android Keystore and file store, WebCrypto and IndexedDB), `composeApp/` and `androidApp/` (manifest, backup and network rules, entry points, clipboard, the Friends screen and its texts), web `index.html`, `Main.kt`.
- **Surroundings:** `deploy/` (compose, Caddy snippet, `deploy.sh` diff since M0), workflows (triggers, permissions, pinning), `.gitignore`, `.claude/settings.json` deny list, secrets and PII scan of tracked files, issue and PR authorship (prompt injection).
- **Open issues** labeled `later` or `review-finding` and the issues that came from SEC findings (read with GET calls).

Actually run: `cargo test --offline --locked` in `crypto/` (62 passed, including the fingerprint known answers and the pinned emoji table), `cargo deny --locked check` (see SEC-M1-2), `javap` on the Ktor 3.6.0 Android engine class from a downloaded jar (see *Checked and fine*). Not run: the Gradle, Android, wasm, `:server:test` and end-to-end suites (see *Not verified*).

## Summary
M1 added the first real attack surface: accounts, sessions, invites, the KeyPackage directory, a member list, local key storage on two platforms, and a trust store for contacts. I found **no critical or high issue and no exploitable flaw in the server, the crate or the client storage**. The server is deny-by-default (an interceptor before routing; unknown paths answer 401), validates every field, binds every SQL value, keeps IPs out of every decision, logs only closed event names, and connects to Postgres as a least-privilege role over SCRAM only. The crate builds the signed auth bytes itself under its own label, validates the origin, subject and challenge, and has no function that signs arbitrary bytes. The contact book fails closed in each state I traced (lying server, rotated observation, reassigned name, key held by another account, damaged record). Storage wraps the snapshot key with a non-extractable platform key and checks the round trip before it registers.

What is left is mostly **claims that go further than the code**, one **time-sensitive supply-chain item**, and the **M0 carry-over that is still open**:
- The one `medium`: the web client's code comes from the same server the Friends screen is meant to catch. The threat model lists "strict CSP and SRI" as a web mitigation in the present tense, though neither exists and SRI would not help against the serving origin. The threat-model row that asks the milestone review to "evaluate SRI / reproducible builds" is answered in SEC-M1-1.
- A RustSec advisory published yesterday (RUSTSEC-2026-0387, `crypto-bigint` 0.5.5) makes `cargo deny --locked check` fail at this commit. It is not exploitable with our ciphersuite, but CI will go red and the fix is an ignore entry, not an update.
- SEC-M0-4 (CI deploy key in the repo checkout, #53) is still open and now matters more because deploys are live.

## Checked and fine
- **Authentication and sessions (ADR-0009):**
  - The deny-by-default interceptor runs before routing and right after the protocol check; the public set is an exact-path match on the raw path, so an encoded or trailing-slash spelling of a public path needs a session (fails closed). Unknown paths answer 401.
  - Challenges are stateless and MAC-checked, single-use, bounded in age (60 s, 5 s skew), and the clock used cannot go backwards. The used set refuses rather than forgets when full.
  - The signed bytes are rebuilt from the server's configured origin, which must pass the canonical rule at startup; the verifier uses the JDK Ed25519 with an explicit small-order list and a canonical-`S` check.
  - Sessions are 256-bit random, only the SHA-256 is stored, 24 h, at most 5 per device. Login order (format, challenge consumed, global bucket, device, signature, per-device bucket on success only) matches the ADR; unknown device, bad signature and stale challenge give one answer.
  - Registration checks the invite before the username is revealed; the resume path needs a signature over a fresh challenge and an exactly matching (key, username) pair.
- **Invites (ADR-0010):** 128-bit `SecureRandom` codes, strict canonical decode, only the hash stored, redemption in one statement under READ COMMITTED, creator-scoped revoke (`created_by = ?` in SQL; one 404 for everything else), limits counted under a row lock, no code or link in logs, `no-store` on responses that carry one.
- **KeyPackage directory (ADR-0012):** the session's device is the only upload target; the credential identity must equal the account's username and the signature key the registered key; 160 KiB limit on the upload route only (exact method and path); claims limited per claimer, pair and target; claim validates before any bucket is touched; all SQL prepared.
- **Member list (ADR-0014):** account from the session, no parameters, deterministic cut at 200, 10 devices per member, `no-store`, nothing logged, no IDOR surface. The client refuses the whole answer on any rule break (sizes, UUIDs, key length, uniqueness across the answer, at most one inviter).
- **Database and deploy:** roles bootstrapped and re-pinned on every migrate; `requireAuth=scram-sha-256`; `logServerErrorDetail=false`; `log_error_verbosity=terse`; secrets as Docker secret files, checked by `deploy.sh` for mode and ownership; containers read-only, `cap_drop: ALL`, `no-new-privileges`; Caddy has no access log, an API CSP, HSTS, `nosniff`, `no-referrer`; `assetlinks.json` holds a placeholder, not a fingerprint. The `deploy.sh` diff since M0 only adds the secret checks and the migrate step.
- **Crate:**
  - `sign_auth` signs only typed content under the label `MLS 1.0 GifItUp auth v1`; every field is validated; no collision with an MLS `SignContent` is possible because the label differs; there is no FFI signing function.
  - `inspect_key_package` bounds the input (16 KiB), requires an exact parse, valid signatures, our suite, an acceptable lifetime range, no last-resort package, and the expected username in a Basic credential.
  - The snapshot is AES-256-GCM with the header as AAD, bounded before decryption, decoded only after authentication, with wiped buffers. The signing key type (`SecretVLBytes`) is zeroized.
  - Fingerprint known answers pass; the emoji table has 256 unique single-code-point entries and its SHA-256 is pinned in a test.
  - `cargo test --offline --locked`: 62 passed.
- **Contact book (ADR-0014):** traced the paths for a swapped key, an added device, a rename, a reassigned username, a key pinned to another account, a lying `more` flag, a rotating observation, a damaged or missing record, the caps, and a concurrent refresh and claim. Each ends in a block or a refusal with the pins unchanged; a made-up name cannot create a blocked entry; the typed `ReviewedObservation` keeps app code from accepting without the holder; the CLI's blind accept is behind an opt-in. The review is captured when it opens, resets its confirmation on change, and turns trust off from the second change. No screen text uses "verified", "safe" or "secure".
- **Client storage (ADR-0011):**
  - Android: AES-256-GCM Keystore key (StrongBox if present, else TEE), randomized encryption, no user-auth binding by design; state in `noBackupFilesDir`; write to temp file, `fsync`, rename, directory `fsync`; wrapped key bound to version and origin by AAD; the wrapping key is never replaced; the save verifies the round trip before the identity is registered; the wipe destroys the key first among the stored items.
  - Web: non-extractable WebCrypto key with a strict type check, strict-durability atomic IndexedDB transactions, an exclusive Web Locks lock that fails closed.
  - `android:allowBackup=false`, `fullBackupContent=false`, extraction rules on all nine domains, `usesCleartextTraffic=false`, only `INTERNET`, one exported activity whose launch intent is filtered, replaced and ignored on `onNewIntent`; `verifyManifestHardening` enforces these in `check`.
- **API client:** the Ktor Android engine sets `setInstanceFollowRedirects(false)` and `setUseCaches(false)` (checked with `javap` on the 3.6.0 jar), so "redirects are not followed" holds there; response bodies are capped before decoding; all decoder errors are caught and mapped without a message; a session is tied to its endpoint.
- **Origin handling:** one strict link parser, no URL library; a link for another origin is never a switch; the signed origin is the configured one; the first registration needs a confirmation that gates the use case.
- **Logging:** no `println`, `Log`, `console.*` or stack trace in any shipped module (grep); the server logs closed `event=` names and exception class names only; the admin command writes the invite link to stdout only.
- **Secrets and injection:** no key, token or provider-key pattern in tracked files; every issue, PR and recent comment is by the owner or Dependabot (no prompt-injection attempts); third-party Actions pinned to SHAs; workflow permissions are least-privilege; no `pull_request_target`; the cargo cache is written from `main` only.
- **Dev CLI:** `contacts-accept` is test-account only and behind `@BlindAcceptForDevCli`; no key or token in its output.

## Not verified
- **Not run:** Gradle (`check`, `allTests`, `:server:test`, `:e2e:test`), Android and wasm tests (cloud-session limits), so the tests the documents cite were read, not executed, apart from the crate's.
- **Alerts:** Dependabot, code scanning and secret scanning alerts could not be read (403 through the proxy). The RustSec finding above comes from running `cargo deny` locally against the current advisory database. No Gradle or npm advisory check was done; #139 (the `ws` pin) is the only one tracked.
- **Repo settings:** the Actions policy (SHA pinning enforced, allowed actions), the `main` ruleset and the `production` environment could not be read.
- **On a device:** Keystore/StrongBox behaviour, the clipboard clearing on Android 10, 13 and 14, `Paint.hasGlyph` on Android 8, which Android release renders which Emoji version, and whether the web renders the emoji table at all (no emoji font is bundled; the web reports every glyph as unknown). All come from documentation and code only.
- **Ktor's JS (fetch) engine:** whether it follows redirects below `followRedirects = false`; the klib in the Gradle cache holds no readable source. The browser strips `Authorization` on a cross-origin redirect, and the web app talks to a single origin, so the exposure is small.
- **The VM:** Caddy's global log block, sshd, the `authorized_keys` line, file modes of `secrets/`, whether the real `assetlinks.json` is in place.
- **The Gradle dependency graph** (`ktor 3.6.0`, `postgresql 42.7.14`, `HikariCP 7.1.0`, `flyway 13.10.3`) was not compared against current CVE lists.
