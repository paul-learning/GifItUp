## Summary
M2 added the second large attack surface: a relay for MLS handshakes and application messages, a push channel, a group state machine on the client, a durable message history, and a public release path (signed APK, web bundle behind a strict CSP). The reviewer found **no critical or high issue and no flaw in the cryptography**. What held up well:
- The server relays opaque bytes under a deny-by-default interceptor, binds every SQL value, takes the acting device only from the session, and bounds every size, count and rate. The WebSocket authenticates in its first frame, never through a URL or cookie, so cross-site WebSocket hijacking has nothing to steal. It bounds frames, handshake and unauthenticated places before Ktor sees the request.
- The crate refuses everything that is not an Add or Remove proposal, any change of a name or key, oversize groups and wrong-epoch messages, and it does not hand back an application message or apply a commit without a staged decision.
- Sealed history records use one random key with HKDF sub-keys, bound to name and origin by associated data, and bucketed sizes. Record names are keyed PRFs.
- Received GIF references are strict (host and path pattern, parser round trip). The fetcher disables redirects and caps bytes. A scanner bounds what any decoder gets, and only the scanned prefix is passed on. Caption bidi and format characters are rejected before display.
- The release path separates the build (no secrets), sign (secrets, no Gradle) and publish (write token, no secrets) jobs. Actions are pinned by SHA. The sign job re-scans the exact file it signs.

The two `medium` findings are both **availability and consent problems that any invited member can cause against any other member, with an honest server**:
- **SEC-M2-1:** the app has no way to leave or delete a chat, so a stranger can fill a victim's 50 group slots (and put zero-click GIF decoding in front of them). The threat model says "the victim can leave a group"; that is true of the server API and the CLI, not of the app.
- **SEC-M2-2:** one stale welcome (the sender added the victim and then removed them before the victim synced) makes the welcome processor stop at that welcome on every run and never acknowledge it, which blocks every later welcome and keeps the inbox full for up to 30 days.

The rest are four carry-overs from M1 that the owner's M1 sign-off scheduled for M2 and that are still open, one missing-decision item (recents and screenshots), and one inexact claim.

## Checked and fine
- **Delivery Service (ADR-0015):**
  - Every route is behind the session interceptor; the device is `call.session.record.deviceId`, never a request field. A malformed group id is the same `404` as an unknown one; non-members get `404` on fetch, status, ack and post (no existence oracle). All SQL is prepared (`DeliveryRepository.kt`).
  - A post runs in one transaction under the group row lock, so seq order is commit order. Retries are matched by (device, client message id) and a SHA-256 over a length-prefixed encoding of the whole envelope, compared with `MessageDigest.isEqual`; a different envelope is `envelope_conflict`.
  - Size and count caps hold at the parser (16 KiB commits and welcomes, 2 KiB application payloads, at most 10 changed devices), the rules (50 devices, 5,000 messages, 2 MiB per group, 8 MiB per sender, 256 KiB per fetch page) and Caddy (1 MB). Body limit 256 KiB only on the exact method and path of the two post endpoints. Limiters are keyed on an authenticated device (maps cannot be filled by strangers) and the slow creation bucket is spent last (#256 SEC-2).
  - The server's envelope fields (`added`, `removed`) are advisory and not trusted by clients: `CommitJudge` compares counts and keys against what the crate parsed, discards on mismatch, and freezes the group.
  - Retention: acknowledged messages, 7-day non-acker rule, 30-day TTL, empty-group deletion, add-log pruning; logs carry only `event=` names and closed reasons.
- **WebSocket (`SocketEndpoint`, `SocketHub`):** exact `GET /ws` with an upgrade header, no query; the token travels in the first frame over TLS, never in the URL; one lookup at a time off the event loop; `isLive` re-check every 25 s and a close on logout; a `HELLO` that is not the first frame, a binary frame or an oversize frame closes the socket; pushes carry group id, seq and kind only. No `Origin` check is needed because no ambient credential exists.
- **Crate (`group.rs`):**
  - Pure-ciphertext wire policy for handshakes too; only `PrivateMessage` is accepted; a message of another epoch is refused before processing.
  - `inspect_commit`: only Add and Remove, identity continuity of the committer's new leaf (name and key), unique signature keys, 50-leaf and 10-change limits, KeyPackage rules repeated for every Add (suite, lifetime, not last-resort, Basic credential with a valid username).
  - Staged commits are applied only by `merge_staged`, a staged commit blocks our own and the reverse, a pending commit survives export (tested), `forget_group` deletes the group's secrets from storage (tested).
  - `inspect_welcome` binds the welcome to the DS group id, requires the welcome sender to be a leaf, bounds sizes before parsing, and says that parsing consumes the KeyPackage.
  - `max_past_epochs` is the OpenMLS default 0 (SEC-M2-7).
- **History (`history.rs`):** AES-256-GCM through the OpenMLS provider, a random 96-bit nonce per seal (the 2^32 bound is noted), HKDF-Expand sub-keys for sealing and for names, HMAC-SHA-256 record names with length prefixes, associated data of header, label, origin and name, 1 KiB buckets, sizes checked before decrypt, inner layout read only after the tag, zero padding verified, secrets in `Zeroizing`. Known-answer tests computed outside the crate pass.
- **Send path (ADR-0016):** seal, history record, snapshot persist, then post; a pending message is re-posted unchanged with the same id; freshness is checked before every seal and ends in read-only on a server answer older than local state. The server's word decides only availability here.
- **Content and media:** `GifReference.of` allows only `https://static[12]?.klipy.com/ii/<hash>/…` with a re-serialisation round trip; `TextRules` rejects control, bidi and format characters (except ZWJ/ZWNJ) and requires something visible; the Compose UI renders text, never markup; no `innerHTML`, `eval` or dynamic script in any shipped module (grep). `KtorMediaFetcher` sets `followRedirects = false`, caps declared and read bytes at 8 MiB, sends no cookies or `Referer`, reports every failure as a closed result. `MediaScanner` bounds canvas (2048), frames (1000), decoded bytes (128 MiB) and steps (500,000) and never throws; only the scanned prefix is handed to the browser's `ImageDecoder`, which is checked again against the scanner's size and frame count. A bug inside compressed data stays the accepted residual (threat model).
- **Web edge (ADR-0018):** one CSP per answer, with no `unsafe-eval` or inline script, one inline style by hash, `img-src 'self' blob:`, `connect-src` limited to the page's own host plus `api.klipy.com` and the three static hosts, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'none'`, `object-src 'none'`; HSTS, `nosniff`, `no-referrer`, no access log; the invite page is `no-store`; the web container is read-only with no capabilities; the `{host}` placeholder is safe because the site address is one literal host (#249 SEC-5).
- **Release (ADR-0019):** `permissions: {}` at the top; a build job with a read-only token and no secrets; a sign job in the `release` environment that runs no Gradle and removes the keystore on every exit; the publish job holds only the write token; the tag text reaches the shell only through the environment; ancestry of `main` is checked twice; APK scan and identity assertions run again on the exact file that gets signed; exactly one signer equal to `RELEASE_CERT_SHA256` and a v3 signature are required; releases are immutable (owner, 2026-11-07, recorded in `docs/ops/release.md`). All third-party actions in `release.yml`, `deploy.yml`, `ci.yml` and `codeql.yml` are pinned by SHA (grep). No `pull_request_target`.
- **Android:** the manifest still asks only for `INTERNET`, exports only the main activity, `allowBackup=false`, `fullBackupContent=false`, extraction rules cover all nine domains, `usesCleartextTraffic=false`, a network security config with system CAs only. The OkHttp engine is created in one place with redirects off, and the hygiene script forbids custom trust, hostname or socket-factory code.
- **Secrets and logging:** no key, token, private-key or provider-key pattern in tracked files (the only hits are the redaction regexes in `scripts/gh-rest.sh` and its test); no `println`, `Log`, `console.*` or stack trace in any shipped module (the server's `Admin.kt` prints to the operator's console by design); `.gitignore` covers `.env`, `*.jks`, `*.keystore`, `deploy/secrets/`.
- **Prompt injection:** every issue, PR (last 100 of each) and comment since 2026-10-24 is by `paul-learning` or Dependabot. None contained instructions aimed at an agent.
- **Dev CLI:** unchanged rules; `chat-*` commands print decrypted text on purpose, for test accounts only (documented).

## Not verified

## Threat-model changes
Proposed edits to `docs/security/threat-model.md` and ADRs (a follow-up PR; the file is high tier):
1. **Accepted-risk row "Delivery Service availability levers", item (2) (SEC-M2-1):** remove "the victim can leave a group without a Commit" or qualify it ("through the server API; the app has no such action yet"), and add the 50-group cap on the client as a lever (a stranger can fill it) with the planned leave and request flow.
2. **Limitations, near "A leaked invite link" (SEC-M2-1):** say that a welcome from a member who is not a friend is joined without consent today, and that the chat then reaches the media decoder.
3. **Limitations, "Group sync state" (SEC-M2-2):** record that an unprocessable welcome must not block later ones, and that the server keeps a welcome after its target was removed (until the TTL, or until fixed).
4. **Limitations (SEC-M2-3):** add "recents thumbnail and screen capture of open chats" (or the decision to protect them).
5. **Security goal 2 (SEC-M2-7):** exact `max_past_epochs` wording.
6. **Supply-chain row (SEC-M2-5):** say that no Gradle, npm or Netty advisory check runs between PRs, and what runs weekly once #89 lands.
7. **Limitations, wipe (SEC-M2-6):** after the reorder, say that the wipe does not wait for the network.
