# ADR-0006: Protocol versioning and the encrypted content schema

- **Status:** accepted
- **Date:** 2026-10-15
- **Issue/PR:** #56 (M0 architecture finding ARCH-M0-4)
- **Amended:** 2026-10-17 (#80, #24): optional `caption` on `gif`, code-point-based text rules (B3a), message references (B9), annotation types (B10). 2026-10-27 (#24, first PR): the content codec is built; B2 and B10 say which parser reads content and B3a which Unicode version is pinned

## Context
`PROTOCOL_VERSION = 1` only appears in `/health`. A client can't tell it is too old, and the only compatibility rule is `ignoreUnknownKeys`: there is nothing about enums, sealed types or defaults. The plaintext inside MLS application messages has no home and no version either: the GIF reference (ADR-0003, Mode B′) and `GroupMeta` (ADR-0002). ADR-0002 left the MLS padding block size open until that format exists. #12 adds the first real endpoints, so this has to be settled first.

There are two separate formats:
- the **wire protocol** between client and server (`:protocol`), which the server reads;
- the **content schema**: plaintext that is encrypted with MLS on the client and that the server never sees.

Constraints: the server is untrusted (CLAUDE.md); a small circle of friends, one server, two clients (Android, web) released together; no new dependency without need.

## Options considered
1. **Version in a path prefix (`/v1/...`)**: lets two incompatible versions run side by side. But a client on a retired prefix just gets an ambiguous 404, a single server gains nothing from parallel prefixes, and WebSocket URLs would need the same scheme.
2. **Version in a request header, server serves a range [min, current]** (chosen): one explicit check with a closed error, works for every HTTP route.
3. **No version, additive changes only**: simplest, but there is no way to tell an old client it must update.

For the content schema: JSON with kotlinx.serialization (chosen, no new dependency), CBOR (kotlinx's CBOR format is still experimental, and size doesn't matter after padding), or protobuf (a new dependency and code generator).

## Decision

### Part A — wire protocol (`:protocol`)
1. **Versions.** `PROTOCOL_VERSION` is an integer that is bumped only for breaking changes. `MIN_SUPPORTED_PROTOCOL_VERSION` is the oldest client version the server still serves; the server serves [min, current]. The server is deployed first. Raising the minimum forces friends to update, so it is an owner decision.
2. **Announcing the version.** HTTP requests send `GifItUp-Protocol: <n>` (`PROTOCOL_VERSION_HEADER`). Browsers can't set custom headers on a WebSocket, so the version goes in the **first client frame**. There is no query parameter, and the rule is that no secret ever goes in a WebSocket query parameter (it would end up in proxy logs). Planned (#21): a size cap on that first frame and a handshake timeout.
3. **Strict parsing (in place since #12).** The header must match `^[1-9][0-9]{0,3}$` and appear exactly once. The raw value is never logged (`installProtocolVersionCheck`, an interceptor on the whole application, so a new route is covered without opting in; a rejected call is finished before routing, so no route-scoped plugin runs for it).
4. **Signalling an incompatible version (HTTP: in place since #12; WebSocket: Planned #21).** `400` with a closed body: `{"error":"client_outdated","minProtocolVersion":n}` when the header is missing, malformed or below the minimum, and `{"error":"server_outdated"}` when it is above the current version. This is 400, not 426: RFC 9110 §15.5.22 requires an `Upgrade` header on a 426, which doesn't fit an app version. WebSocket: private-use close codes (RFC 6455 §7.4.2) `4001` (client outdated) and `4002` (server outdated). The check covers every route except `/health`, which stays unauthenticated and additively reports `minProtocolVersion` so a client can check at startup.
5. **No downgrade.** A client sends exactly one version and never retries with an older one: `server_outdated` means stop and show an error. A server-supplied `minProtocolVersion` is untrusted: the client bounds it and shows only its own built-in "please update the app" text, never server-supplied text or links.
6. **JSON configuration.** `ProtocolJson` is the single configuration for both sides, and every `JsonBuilder` flag of kotlinx.serialization 1.11 is set explicitly, except `prettyPrintIndent`, which only applies with `prettyPrint` (formatting and naming flags at their defaults: `prettyPrint = false`, `namingStrategy = null`, `useAlternativeNames = false`, `allowStructuredMapKeys = false`, `useArrayPolymorphism = false`, `classDiscriminatorMode = POLYMORPHIC`). The ones that matter for compatibility and input safety:

   | Flag | Value | Why |
   |---|---|---|
   | `ignoreUnknownKeys` | `true` | Fields added by a newer peer don't break older readers |
   | `encodeDefaults` | `true` | The wire is explicit; a reader never fills in its own, possibly different, default for a field the writer knew |
   | `classDiscriminator` | `"type"` | Stable name for sealed types |
   | `explicitNulls` | `true` | `null` is written, not omitted |
   | `coerceInputValues` | `false` | Would turn an invalid `null` or unknown value into a default and hide garbage input |
   | `exceptionsWithDebugInfo` | `false` | No input excerpt in lexer error messages (default `true`). Messages can still name unknown enum values and type names, so A8 applies regardless |
   | `isLenient`, `allowComments`, `allowTrailingComma`, `allowSpecialFloatingPointValues`, `decodeEnumsCaseInsensitive` | `false` | Strict input; no second interpretation of the same bytes |

7. **Compatibility rules.** Each has a test in `protocol/src/commonTest/.../CompatibilityRulesTest.kt`.
   - **Additive changes** (a new field with a default, a new enum value or sealed subtype under the rules below) don't bump the version. Removing or renaming a field, or changing its type, meaning or optionality, is breaking and bumps it. A Kotlin property rename keeps the wire name with `@SerialName`.
   - **Fail closed for security-relevant fields.** A field whose absence would weaken a security check (for example ADR-0002's freshness anchor) gets **no permissive default**. Either its absence fails closed, or adding it is a breaking change. Its KDoc states which. Otherwise an older or rolled-back server could switch off a check just by omitting the field.
   - **Enums that can grow** use `FallbackEnumSerializer`: an unknown value decodes to `UNKNOWN` instead of failing the whole payload. Matching is case-sensitive on the wire name: the constant name by default, or an explicit `wireName` (since #12, `ApiErrorCode` uses lowercase wire names such as `bad_request`). Encoding `UNKNOWN` throws. Receivers handle `UNKNOWN` as "not supported" with an exhaustive `when` and no `else`, and the server rejects `UNKNOWN` in requests with a closed 400 (`requireKnown`, in place since #12; each endpoint applies it to its growable request fields). Enums that are closed by design stay plain and strict, and say so in their KDoc.
   - **Sealed types** have a stable `@SerialName` per subtype (never the class name) and an `Unknown` subtype registered as the `polymorphicDefaultDeserializer` with `UnknownSubtypeSerializer`, only for a present type name (a missing or `null` `type` fails). It consumes and drops the input, keeps no fields, and can't be encoded, so nothing a newer or malicious peer wrote is shown later.
8. **Decode errors are closed.** kotlinx.serialization's exception messages contain the input (`JSON input: …`). So decoder exceptions' `message`/`cause` are never logged, shown or returned. In place since #12: a StatusPages handler maps every failure to a fixed status and a closed `ApiErrorCode` body (`{"error":"bad_request"}` for decoding failures, `{"error":"internal"}` for anything unhandled, which logs only the exception class), with tests that a marker in the input appears neither in the response nor in the logs.
9. **Input limits (in place since #12).** A request body limit enforced **before** deserialization (Ktor `RequestBodyLimit`, 16 KiB default, routes with bigger bodies set their own), with 413 tests for a declared `Content-Length` and for a chunked body without one. The Netty engine also limits the request line and header size, and a connection that doesn't deliver a complete request within 10 s while nothing is in flight is closed: silent, half-sent, trickling and idle keep-alive connections alike (`RequestDeadlineHandler`; Ktor's own read timeout only fails an active call, #68 SEC-15). Caddy's 1 MB body limit (ADR-0005) applies only to traffic that goes through Caddy, so the server doesn't rely on it.

### Part B — encrypted content schema (`:shared`, data layer; the codec is built since #24, its first PR; the message store and the send and receive pipeline follow in the next PRs of #24)
1. **Location.** `app.gifitup.shared.data.content` in `:shared`. It is plaintext *before* MLS encryption, not a ciphertext format, so encryption and padding stay in `crypto/` (crypto boundary unchanged). Content types never go into `:protocol` (CLAUDE.md), and `scripts/check-repo-hygiene.sh` fails if `server/build.gradle.kts` or `protocol/build.gradle.kts` (the server's only project dependency) mentions `:shared`. It is a text check: it catches the usual spellings, not every possible build-script construct, and it can't see content types written directly into `:protocol`; that part stays a review rule.
2. **Encoding.** UTF-8 JSON with its own `ContentJson` (same flags as A6), used to **write** content. The bytes are decoded strictly (`decodeToString(throwOnInvalidSequence = true)`), and the size is checked **before** parsing. Content is **read** by `StrictJson`, a small strict RFC 8259 parser of our own (B10), because kotlinx.serialization can't reject duplicate keys.
3. **Envelope.** `{"v":1,"type":"<name>",...}`. Field order on the wire carries no meaning (kotlinx writes `type` first). `v` is the content schema version, independent of `PROTOCOL_VERSION`; it is **required with no default**. v1 types:
   - `gif`: `provider`, `slug`, `url`, `width`, `height`, validated exactly as in ADR-0003 and the [GIF spike](../spikes/gif-provider.md). The "raw URL string" is the decoded JSON string value, which is exactly the string that gets fetched. Optional **`caption`** (#80): a short plain-text line shown below the GIF. Absent or `null` means no caption (our writers emit `"caption":null` because `explicitNulls = true`; older writers omit the field); anything else that isn't a JSON string makes the message `Invalid`. Rules: B3a, trimmed, at most **120 code points** after trimming; empty after trimming means no caption; anything over the limit or breaking B3a makes the whole message `Invalid` (fail closed, the GIF isn't shown without it). The **80 user-perceived characters** of #80 (grapheme clusters, so an emoji counts as 1) are a **sender-side UI limit** only (#25): grapheme segmentation differs between ICU versions and browsers, so receivers never check it. The sender enforces both limits. A caption never exists without a GIF: there is no text-only type.
   - `group_meta`: `name`, trimmed, 1–64 code points, rules B3a. It is rendered as plain text with bidi isolation, and every rename shows "<MLS-authenticated sender> renamed the group". It is ignored in 2-member chats, which show the contact's name.
   - `blob_gif` (M3, ADR-0003 Mode A) is added later as a new type.

3a. **Text fields** (`gif.caption`, `group_meta.name`; built in #24 as `TextRules`). Sender-supplied text is checked over **Unicode code points** (scalar values of well-formed UTF-16), never over UTF-16 units: Kotlin's `String.length` and `Char.category` see a non-BMP code point as two surrogates, so they would count an emoji twice and miss every non-BMP format character. The check is one **shared pure-Kotlin implementation** in `:shared` with its own fixed table, not the platform's character tables: JVM, Android and Kotlin/Wasm ship different Unicode versions, and the same text must be valid on all of them or on none.
   - **Pinned Unicode version:** the latest released Unicode version when #24 generates the tables (CLAUDE.md: latest stable). **Pinned: 18.0.0** (owner decision, 2026-10-27: "use 18.0.0"). The committed header of `UnicodeTables.kt` lists the version and the SHA-256 of each source file; `shared/unicode/generate_tables.py` regenerates it. The files came from the `unicode-org/unicodetools` repository, as unicode.org was not reachable from the build sandbox, and the owner compares them with unicode.org before merging. The 17.0.0 files give identical tables for the three properties used. Every table below is generated from that version's UCD files (`UnicodeData.txt`, `PropList.txt`, `DerivedCoreProperties.txt`) and committed as a fixed table, together with the version and the SHA-256 of each source file. Moving to a newer version is a deliberate change with its own review.
   - **Rejected code points:** an unpaired surrogate; Cc (U+0000–U+001F, U+007F–U+009F); Zl (U+2028) and Zp (U+2029); all 66 noncharacters (U+FDD0–U+FDEF and U+nFFFE/U+nFFFF for every plane n = 0–16); every Cf code point except U+200C and U+200D (from the Cf table, which includes the bidi controls U+061C, U+200E–U+200F, U+202A–U+202E, U+2066–U+2069); and, as **explicit ranges** regardless of their category, because parts of them are unassigned and an unassigned code point isn't Cf: the whole tag block U+E0000–U+E007F (it can hide invisible ASCII text, at the cost of the Scotland/Wales flags), U+13430–U+1343F, U+1BCA0–U+1BCA3 and U+1D173–U+1D17A. #24 has one test vector per range, run on JVM **and** wasmJs.
   - **Allowed Cf exceptions:** U+200D ZERO WIDTH JOINER, so emoji ZWJ sequences (👨‍👩‍👧, 🏳️‍🌈) work, and U+200C ZERO WIDTH NON-JOINER, which Persian and some Indic spelling need (owner decision, 2026-10-17). Neither is a bidi control or can reorder text.
   - **Order of the checks:** (1) the raw decoded value is checked against the rejected set, so a newline or U+2028 anywhere, also at the ends, makes it `Invalid`; (2) then leading and trailing White_Space code points (from `PropList.txt`) are trimmed; (3) then the code points are counted. Senders send the trimmed value; a received value with extra leading or trailing spaces is still accepted after trimming. #24 test vectors: `"hi\n"` → `Invalid`, `" hi "` → `"hi"`.
   - **Not blank:** a value that is non-empty after trimming must contain at least one code point that is neither White_Space nor Default_Ignorable_Code_Point (`DerivedCoreProperties.txt`; that covers ZWJ, ZWNJ, variation selectors, Hangul fillers such as U+3164, U+034F and the Mongolian variation selectors) nor U+2800 BRAILLE PATTERN BLANK; otherwise it is `Invalid`, so a group name or caption can't look empty.
   - **Accepted residuals:** unassigned and private-use code points are allowed (no table can know which ones a font draws), and combining marks can stack into a tall glyph (the UI clips text fields to one line of bounded height, #25), and variation selectors stay allowed (emoji need U+FE0F), so a caption can carry up to about one hidden byte per selector; ZWJ and ZWNJ, inserted between other characters, are another such hidden channel (about one bit each). None of them changes what the text shows as plain text. All three accepted by the owner, 2026-10-17.
   - **Rendering:** plain text only, with bidi isolation, no links or formatting. Single line follows from rejecting Cc, Zl and Zp.
4. **No identity and no timestamp in content.** The sender is the MLS-authenticated sender only. There is no sender, group or "sent at" field. The displayed time is assigned by the server and therefore untrusted (threat model, Limitations).
5. **Unknown or invalid → placeholder, never crash.** Annotation types (B10) are handled first: a payload whose `type` is a string starting with `ann_` follows B10 and never produces a placeholder. For everything else: `v < 1`, malformed JSON or UTF-8, content over the size cap, or a failed field check → `Invalid` ("message unavailable"). A missing or `null` `type` is `Invalid` too, never `Unknown`: the default deserializer only applies when a type name is present. `v` above the supported version or an unknown `type` → `Unsupported` ("update the app"); the `v` check runs first, so a `v=2` payload of a known type is never rendered. The codec boundary catches `SerializationException` **and** `IllegalArgumentException` (kotlinx throws the latter for some malformed input, such as a non-string `type`). Neither carries any input text, and no sender-supplied fallback text is ever shown.
6. **`authenticated_data` stays empty** for application messages. MLS sends it in the clear and outside the padding.
7. **Padding (Planned #11; the code is still at the spike value of 256).** MLS `padding_size = 1024`, set in both the create and the join config. In OpenMLS 0.9.1, `padding_size` is a block size: the serialized content plus its auth data (signature, confirmation tag) plus the AEAD tag is padded up to a multiple of the block size (`encode_padded_ciphertext_content_detached` in `framing/private_message.rs`; the receiver rejects non-zero padding, `framing/codec.rs`). With the maximum encoded content of **896 bytes**: 2 (length prefix) + 896 + 2 + 64 (Ed25519 signature with its length prefix) + 0 (an application message has no confirmation tag, and its absence writes no bytes: `FramedContentAuthData` in `framing/mls_auth_content.rs`) + 16 (AES-GCM tag) = 980 ≤ 1024. The one-block maximum would be 940 bytes; 896 keeps a margin. So with `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, every v1 message is exactly one block. Changing the ciphersuite means recomputing this cap. **Claim and limits:** a passive server can't tell v1 content types apart by ciphertext length. Timing and context (a `group_meta` right after a Commit) can still give it away. Planned (#11): a test of the full serialized `MlsMessageOut` length for the smallest and largest valid payload of each v1 type, and a sender-side reject at 897 bytes. 1024 rather than 512 (512 would also fit every v1 type, with a cap of about 420 bytes) buys headroom for future types at about 1 KiB per message.
   **Largest `gif` (with #80's caption, as senders send it: trimmed, B3a):** compact `ContentJson` with the longest valid fields is 363 bytes plus the caption's bytes: the longest URL the ADR-0003 regex allows is 137 characters (`https://static1.klipy.com/ii/` + 32 hex + `/xx/xx/` + a 64-character name + `.webp`), the slug 128, `width`/`height` 2048, and `"caption":""` (with `"caption":null` it is 365). kotlinx writes non-ASCII as raw UTF-8 and escapes only control characters (rejected by B3a), `"` and `\` (2 bytes each), so a caption code point costs at most 4 bytes: 363 + 4 × 120 = **843 ≤ 896**, still exactly one block. A received caption with extra untrimmed spaces is still bounded by the 896-byte cap, which the codec checks before parsing. In place (#24): `ContentCodecTest.theLargestValidGifIsOneBlock` encodes this maximal payload with the real `ContentJson` (120 × a 4-byte emoji: 843 bytes; 120 × `"` or `\`: 603; no caption: 365) and asserts ≤ 896 bytes; that 896 bytes is one padding block is tested in `crypto/` (#11). A new field on `gif` must redo this sum.
8. **Evolution.** New optional fields and new types are additive. A field that restricts what the recipient may do (expiry, tap-to-load) must not be silently ignored by older clients, so it needs a new `type` or a `v` bump, which makes old clients show the placeholder. v1 has no capability negotiation: a sender on a newer `v` makes older members see the placeholder. That is acceptable for a small circle. MLS `required_capabilities` is an option later. Annotation types (B10) are the exception: older clients drop them silently, so they are only for additions that are safe to miss.
9. **Message references** (done in #22 for `crypto/`, planned in #24 for the store). Reactions (#88) and later replies point at a message by its **message reference**:
   - **Definition:** `ref = SHA-256("GifItUp v1 message ref" ‖ MLSMessage bytes)`, computed in `crypto/` with the OpenMLS crypto provider's `hash(HashType::Sha2_256, …)` (nothing hand-rolled), for application messages only. The sender hashes the bytes it posts; a recipient hashes the bytes it received, only **after** they parsed exactly (`tls_deserialize_exact`) and `process_message` accepted them. In content it is unpadded base64url of the 32 bytes and must fully match `^[A-Za-z0-9_-]{42}[AEIMQUYcgkosw048]$` (43 characters, canonical: the unused trailing bits are zero).
   - **Why the raw bytes are stable:** OpenMLS 0.9.1 builds `tls_codec` 0.5 with its `mls` feature, which rejects non-minimal variable-length encodings (`check_min_len`); `framing/codec.rs` accepts only MLS 1.0; `PrivateMessageIn` has only fixed-width fields and length-prefixed vectors; and `group_id`, `epoch`, `content_type` and `authenticated_data` are bound by the AEAD. So the server can't hand two recipients different accepted encodings of one message, and every member computes the same reference. Planned (#22): a regression test that re-serialising a parsed message gives exactly the input, so an OpenMLS or `tls_codec` change that drops this fails CI.
   - **What it guarantees, and what not:** no collisions or second preimages (SHA-256), and it is bound to one group and epoch through the ciphertext. It identifies one **delivered ciphertext**, not an authored message: every member can derive every sender's ratchet keys, and the MLS signature covers neither `generation` nor `reuse_guard`, so a malicious member can re-encrypt another member's message within the same epoch, and recipients see a second copy, attributed to that sender, under a different reference. After a local state rollback, a replayed message can arrive again under the same reference. Both are existing MLS properties (threat model, Limitations).
   - **The server can compute every reference** (it stores the ciphertext). A reference is therefore **content**: it never appears in a server-visible field, request, header, push payload, `authenticated_data`, log or `:protocol` type. Otherwise the server could link a reaction or reply to its exact target. An exception needs its own ADR. (A random id chosen by the sender wouldn't have this property, but it would be forgeable by any member, cost every message 30 bytes and need its own group binding; hence the hash.)
   - **Receiver rules:** references are looked up only in the MLS group that processed the message (its MLS group id, never a group id from the server's envelope). A reference to an unknown message, to another group's message or to a type that can't be a target makes the annotation be dropped (B10). The local store is keyed on (MLS group id, reference), first seen wins, and inserting the same reference again changes nothing.
   - **Retries:** a send whose outcome is unknown (timeout) is retried with **the same MLSMessage bytes** as long as the epoch hasn't changed, so it keeps its reference. The outgoing bytes are therefore persisted in the same atomic write as the MLS state after encryption (#16). A copy the server already stored reaches recipients twice; they reject the second as a replay, and that error is **acknowledged and dropped silently**, never shown or quarantined (#22). Only a send the server confirmably rejected, or one from an epoch that has moved on, is re-encrypted, and it gets a new reference.
   - **Only this label:** other hashes over messages (for example a freshness value the client reports to the server for rollback detection, #21/#22, ADR-0002) use their own domain-separation label and are never message references, so they can't become a server-visible copy of one.
10. **Annotation types** (the rule is built in #24, the first type is #88). Some content attaches to another message instead of being one: reactions (#88), and similar later. Unknown types normally show "update the app" (B5), which would put a placeholder into every chat for each reaction a newer client sends. So:
    - A content type whose name starts with **`ann_`** is an annotation (first: `ann_reaction`, defined in #88; until then every `ann_` type is unknown and dropped). Every annotation type has a required `target`: a message reference (B9).
    - **One parse:** the codec parses the bytes once with `StrictJson` into a tree, rejects duplicate keys anywhere (→ `Invalid`; keys are compared after unescaping, so `"\u0074ype"` duplicates `"type"`) and nesting deeper than 8, reads `type` from that tree for the `ann_` check and decodes from the same tree, so the bytes can't be read two ways (test: two `type` keys, escaped duplicates, duplicates in unknown fields). Only the fields the schema reads are kept; numbers are plain integers or "not an integer", never floating point.
    - **Receiver rule, the same for every `v`:** an annotation that is of an unknown type, has a `v` above the supported one or below 1, fails validation, or whose `target` doesn't resolve (B9) is **dropped silently**: no placeholder, nothing stored. A dropped annotation counts as **processed successfully**: the message is acknowledged and never retried or quarantined. There is no buffer for annotations that arrive before their target; they are dropped for good, because a buffer would be memory that any member can fill. A malformed envelope (bad JSON or UTF-8, a missing or non-string `type`, over the size cap) is still `Invalid` (B5), since its type can't be read.
    - **Bounded state:** an annotation type defines how much state it keeps per (MLS group, MLS sender, target, type), for example #88's "one reaction per person per GIF, latest wins", so flooding many annotations doesn't grow the store without bound. The server can reorder or withhold messages, so two members can end up with different annotation state (for example a reaction removed for one of them and not the other). That is a limit of annotation integrity, not of message integrity.
    - **What an annotation may be:** only an optional **addition** to its target, so that an old client that drops it still shows everything correctly. Anything that changes what the target means or restricts what a recipient may do (edit, delete or retract, caption change, expiry, tap-to-load) must never be an annotation: it needs a visible type or a `v` bump (B8).
    - **Why a prefix, not an envelope flag:** a flag would need rules for known types that carry it (`{"type":"gif","annotation":true}`); the prefix is part of the type name that B5 already reads. A malicious member gains nothing from it: it can only make its own messages invisible to old clients. The server can't see the type at all, and annotations are padded like every message (B7), so a passive server can't tell a reaction from a GIF by length.

## Consequences
- #12 implements the version check, strict header parsing, closed error bodies and the body limit; #21 the WebSocket handshake; #24 the content codec and its validation; #11 the padding value and length tests. Each issue lists these items as acceptance criteria.
- From the 2026-10-17 amendment: #24 implements the caption codec, the shared B3a text check (also for `group_meta.name`), the maximal-payload length test, the B10 drop rule and the B9 store rules; #22 made `crypto/` return the message reference from encrypt and process (with the re-serialisation test and a JVM/wasm test that both compute the same reference for the same bytes) and the B9 retry rule, with replays of a retried send acknowledged silently; #16 persists the outgoing bytes atomically with the MLS state; #25 the caption input (live 80-character counter, "+ add caption", one-tap send without one) and rendering below the GIF; #88 the first annotation type.
- Every new wire field needs a decision: additive with a harmless default, or fail-closed/breaking. Reviewers check this.
- **Metadata:** the version header shows the server the coarse app release of each request. It is needed to refuse incompatible clients, and it is the same for everyone on a release. If the web client is ever served cross-origin from the API, CORS must allow exactly this header (no wildcard). Content stays invisible to the server. Padding to 1024 makes every v1 application message the same length. The 2026-10-17 amendment adds none: captions and annotations are inside the MLS content and its padding block, and message references stay out of every server-visible place (B9).
- Forcing an update by raising the minimum version locks out friends who haven't updated. The owner decides when.
- The `Unknown`/`UNKNOWN` fallbacks make old clients tolerate new data, but nothing can be rendered from it. That is deliberate.
