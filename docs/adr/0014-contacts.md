# ADR-0014: Contacts, the member list and the contact book

- **Status:** accepted (PR 1: server side and client API; PR 2: the contact book and the claim check; PR 3: the emoji fingerprint in the crate; PR 4: the Friends screen, see *Unblocking* and *The Friends screen*)
- **Date:** 2026-10-22
- **Issue/PR:** #18 (three PRs). Round-0 plan review: SEC-1 to SEC-9.

## Context
A member needs to see who they can talk to, and the app needs a record of which key belongs to which person so that a key swapped by the untrusted server is noticed (ADR-0002 "Member validation" hands this to "the TOFU record (#18)"; ADR-0012 hands over the signature key of every claimed KeyPackage). Two facts shape the design:
- Any member can already claim any other member's KeyPackages by username (ADR-0012, owner decision "one community"). A list of people is therefore a convenience, not an access boundary.
- A username is not an identity: a deleted name can be registered again by anyone with an invite (threat model, SEC-58 of #74). A contact must be keyed by account id and key.

## Options considered
- **Who the list shows** (owner decision, 2026-10-22: "only my invite neighbours and add an issue to work on a contact request / discovery process"; "Inviter and invitees only"): the caller's inviter and the accounts they invited (chosen), vs. every member (tells every member who is on the server, and the server then holds a directory it does not need), vs. members of shared groups (no groups exist yet). Everyone else stays reachable by name until the discovery issue decides how people find each other.
- **A key changes** (owner decision, 2026-10-22: "Block and warn, you can accept"): block and warn (chosen), vs. warn and continue (the warning gets clicked away), vs. block with no way back (a reinstall would orphan a friend).
- **A fingerprint from the server:** refused. A fingerprint the server computes proves nothing (a lying server shows a matching fake), and computing one on the phone needs the crypto crate (crypto boundary, ADR-0007). Fingerprints are #31.
- **Split:** three PRs (owner decision), which became four when the owner chose a local fingerprint: server and protocol (PR 1), the contact book and the claim check (PR 2), the fingerprint in the crate (PR 3), the Friends screen (PR 4).

## Decision
### The member list (`GET /members`)
- A session is required; the account is the session's and the request carries nothing. The answer holds the caller's inviter (first, if there is one and it still exists) and the accounts with `invited_by = caller`, then by username in byte order, ties by id (one deterministic order, so the cut is the same on every request). At most 200 members and `more: true` if cut; per member the account id, username, `relation` (`inviter`, `invitee`, growable, unknown = `UNKNOWN`) and at most 10 devices (id and signature key, oldest first). `Cache-Control: no-store`. Direct edges only: no grandparents, siblings or grandchildren.
- **`relation` is the server's statement and is display only.** No check in the client may depend on it, and nothing is trusted because the server calls it "your inviter" (SEC-7).
- **This is a view, not an access control.** The claim stays open to every member by username, with its 404 oracle and limits (ADR-0012). Docs and screens must not call the list a privacy boundary.
- **Metadata:** nothing new is stored. The tree edge was already known to the server and to both ends; what changes is that it is now served to both ends permanently (the invite list shows `used_by` for 30 days), an invitee learns which account created their link, and both sides get the other's device signature keys (already claimable by username).
- The client refuses the whole answer, never a part, when it breaks any rule: body at most 256 KiB (the largest legal answer is about 252,000 bytes, so a new per-member field needs a new cap; SEC-12), at most one `inviter`, at most 200 members and 10 devices each, canonical UUIDs, the username rule, canonical base64url keys of exactly 32 bytes, and every account id, username, device id and key unique across the answer (SEC-5).

### The claim response carries the account id
`POST /key-packages/claim` returns `accountId` next to `devices`, so the client can tell a new device of a known account from a new account under the same name. The field is **required**: a response without it does not decode, and the client treats that as a refusal and never as "unknown, so fine" (SEC-2). The server is deployed first. An older client ignores the extra field (`ignoreUnknownKeys`), so this is additive for old clients and fail-closed for new ones (ADR-0006). The cost is a rollback: a new client against a server rolled back to before this field fails every claim as `MALFORMED_RESPONSE` until the server is deployed again, which is the intended refusal. The id is a random UUID: it is no credential and no server input anywhere; keep it out of logs and URLs.

### The contact book (PR 2)
- One record per account id: username, status, devices as `signature key → device id` (the **signature key** is the authenticated value from the KeyPackage credential; the device id is a label only), first and last seen, and a separate **pending observation** for a blocked entry. Stored in the `LocalStore` under one versioned key, plain (public data); the integrity gaps are not the encoding but the failure modes below.
- **Rules**, all fail closed, applied to both sources of a sighting (the list and every claimed KeyPackage):
  1. Unknown account id: a sighting in the **list** is kept as `UNCONFIRMED` and becomes a pin only on a user action (adding the contact) or a claim; a sighting in a **claim** pins it (first sight; TOFU, so an active server can still serve a forged key before the first sighting). Otherwise a lying server could list a fake `alice` before the user claims the real one, and the real one would arrive as `USERNAME_REASSIGNED` and need the blind unblock (SEC-10). An `UNCONFIRMED` entry is never evicted over a pin and never blocks a claim: a claim that shows another account under the same username replaces it and is not a `USERNAME_REASSIGNED` (tested in PR 2). `UNCONFIRMED` entries have their own cap (100) and are reset on the next complete list, so a lying server cannot fill the book with them (SEC-13).
  2. A pinned account with a different key under a pinned device: `KEY_CHANGED`.
  3. A pinned account with a key it did not have: `DEVICE_ADDED`, blocked too, because until multi-device (#72) an account has one device and a second one is what a ghost device looks like.
  4. A pinned account id with another username: `RENAMED`.
  5. A username pinned to account X now belonging to account Y: Y is `USERNAME_REASSIGNED` (SEC-58), X is `GONE`, its pins kept. Always shown with both accounts.
  6. A signature key pinned to account X shown under another account or username: `KEY_CONFLICT` (the server's UNIQUE constraint does not bind a lying server).
  7. A pinned device missing from a **complete** list: `DEVICE_GONE`; a pinned account missing: `GONE`. Information only, and only when `more` is false (SEC-5). `GONE` returns to normal on a reappearance with identical pins.
  8. A list that names the caller's own signature key or own username is refused as a whole (SEC-11, SEC-20): the client knows its own key and name, not its account id, and the server cannot list us as someone else.
  9. A claim without a valid `accountId`, or whose username differs from the pinned username of that account id: refused.
- **`BLOCKED` is sticky:** a later good sighting does not clear it, and the pending observation never overwrites the pin (SEC-3). A claim for a blocked contact is refused **before** the request, so the target's KeyPackages are not burned (SEC-6); a first-contact conflict can only be seen after the KeyPackage is consumed, which is the cost of claim-then-check.
- **Failure modes (SEC-4):** a missing, oversize, corrupt or unknown-version record means "contact book unavailable" and every claim is refused; it is never read as an empty book, except after an explicit wipe. Pins are never evicted; at the pin cap (500) a new account is refused, and list-only sightings have their own cap (100). All updates run under one lock and write atomically; a failed pin write makes the claim return `Blocked`, never `Usable` (the KeyPackage is already consumed). The book lives and dies with the identity: the same wipe (ADR-0011).
- **Unblocking (owner decision, 2026-10-22: "a) local fingerprint").** The crate computes a fingerprint of a signature key on the device (PR 3, `crypto/`), and the Friends screen (PR 4) shows the pinned and the new value side by side, for the rule 5 case both accounts. The button says what it does ("Trust the new key"); the real check is out of band. `accept` takes the observation the user was shown and pins exactly that, only if it is still the pending one (structural equality; Kotlin common does no hashing, ADR-0007), else it asks the user to look again (SEC-3). Until PR 4 **no app screen can accept**: `AcceptContact` exists in `:shared` for the dev CLI only (`contacts-accept`, test accounts, says it accepts blindly), and a test fails if an app module references it.

### Where the book lives (PR 2)
- The record is created empty **in the same atomic write as the first write of the identity** (a registration), replacing any leftover of an earlier identity, and deleted with it (`clear`, and the wipe). Later identity saves (every KeyPackage refill) never touch it, so a missing record next to an identity is `Unavailable` and claims are refused; a damaged one stays damaged. This catches a crash between two writes and a partial loss; it does not catch an attacker with write access to the store, who can delete the identity and the book together or replace the book wholesale: that is the trust level of the snapshot key (ADR-0011) and is not defended. **There is no migration:** an identity from before PR 2 has no record, so its claims fail as unavailable until the device is wiped and registered again (alpha, no friends yet; a migration would be the one place where "missing" turns into "empty").
- **Accepted limits:** a rolled-back copy of the record (a restored profile or file) silently drops pins and blocked states; the record carries no freshness counter. A second app instance on the same store could lose an update; ADR-0011 prevents it with the device lock (Web Locks on the web), and the contact store opens only after that. The dev CLI's file is guarded by its state-dir lock.
- **Whole-claim judgement (SEC-17):** one claim returns several devices and is judged once: any conflict, a username different from the pin, a key held by another account, or a first claim with more than one usable device blocks the whole claim, hands on no KeyPackage and pins nothing. Duplicate keys inside one claim are refused. The pre-check for a blocked name takes the lock and releases it; the authoritative check and the pin are one `update` after the request, and the lock is never held across a request (SEC-18).
- **No sticky entry from an impostor (SEC-22):** a list entry for an unknown account that carries a key pinned to another account is dropped, and a claim whose key is pinned to another account is refused with nothing stored: such an entry could never be accepted and would block its name for good. `accept` also refuses a username that another live account holds, and keeps the pins of devices the observation does not name (a claim shows only usable devices) (SEC-23).
- A damaged record stays damaged, so claims on that device stay refused until the identity is wiped; a reset belongs to the screen in PR 4 (SEC-24, accepted).
- A pinned account that is missing from a complete list becomes `GONE`; a `DEVICE_GONE` per device is not tracked (information only, no behaviour). At the pin cap a new account is refused as `BOOK_FULL`.

### Fingerprint (PR 3)
- **Owner decisions:** 2026-10-22 "a) local fingerprint" (see *Unblocking*); 2026-10-23, on what the user compares: "since its a silly content app, id like it if the user were to compare emojis, in fact maybe make it a rule, if we do something crypto based but user facing, if we can use a silly option, we should consider it". So the fingerprint is shown as emojis. The "rule" is the owner's to word (it would go into `CLAUDE.md`); the principle is applied here: a playful presentation is fine as long as it does not weaken the check or its accessibility.
- **Algorithm (`crypto/src/fingerprint.rs`, `MlsClient.fingerprint`):** `SHA-256("gifitup/fingerprint/v1" || 0x00 || key)`, the first 12 bytes, each an index into a 256-entry emoji table: 96 bits. The key is exactly 32 bytes (Ed25519, the only key type of ADR-0002's ciphersuite) or the call is `InvalidInput`; another key type or length is a new `v2` label, never a silent reuse. Key only, not the username: a reassigned name with a different key gives different emojis, and the same key under another account is already `KEY_CONFLICT`. No iteration: the input is a public key and there is nothing to stretch. It is a method of the client (same panic guard and poisoning as every call), pure, and reads no state.
- **What 96 bits mean:** a forged key whose fingerprint equals a given one costs about 2^96 key generations **if all 12 emojis are compared** (a server that targets any one of N victims pays about 2^96/N, still out of reach). Matching only the first k costs about 2^(8k): 4 emojis are 2^32. The screen therefore shows all 12 as one block in a fixed order with no "first few match" affordance, and its copy says "all 12 must match".
- **What the user checks:** the contact reads out the emojis (with their names) that their own phone shows for themselves, and the user compares them with the ones shown for that contact. Old versus new side by side only shows that they differ. "Your emojis" come from the local identity's own signature key, never from a server answer. Until multi-device (#72) an account has one device; a contact with several devices (which the book blocks, rule 3) shows each device's set, and every one has to be verified.
- **The table is part of the format.** `crypto/fingerprint-emojis-v1.tsv` is the list (256 entries: index, code point, name); the crate pins its SHA-256 in a test, `FingerprintEmojis` holds the same list, and a JVM test compares the two, so the table can't change without a change under `crypto/`, a high-tier path. The label `v1` and the table change together. Rules: one code point with default emoji presentation (no variation selectors or joiners), Emoji 4.0 or older, no people, hands, faces, flags, skin tones, clocks, zodiac signs or colored shapes, unique emojis, unique names, unique first words; none is an `Emoji_Modifier_Base`, and every one has `Emoji_Presentation=Yes` and Emoji version 4 or older (all three checked with Unicode and emoji data when the list was made; a test can't check them without that data). **Residual:** the Kotlin test that compares the list with the crate's file lives under `shared/`, a normal-tier path, so a PR that edits only the Kotlin list and weakens that test would not touch `crypto/`; the owner may want that path on the high-tier list. Emoji 4.0 is a deliberately conservative bound for the minSdk 26 baseline: which Android release renders which Emoji version was not verified here.
- **Rendering limits:** a device that lacks a glyph draws the same box for several emojis, vendors draw the same emoji differently, and the web app may have no color emoji font. So the name is always shown with the emoji and counts in the comparison; the screen (PR 4) checks glyph support where the platform can and shows the names prominently where it can't. Some pairs look alike even with glyphs (a ram and a goat, a rat and a mouse); the names tell them apart.
- **Tests:** known answers made outside the crate (Python `hashlib`) for four keys including the all-zero key and a high-bit key, in the crate and again through `:mls` on the JVM and the web; wrong lengths; unsigned index handling in Kotlin; the table's rules and its comparison with the crate's file. The test double `FakeMlsClient` returns the first 12 bytes of the key and does not hash.

### The Friends screen (PR 4)
The one place where a user trusts a blocked friend again. Rules, each from a round 0 finding:
- **Emojis come only from saved keys (SEC-42).** A friend only the server's list has shown is "not saved yet" and has no emojis: comparing a listed key proves nothing about the key a later claim pins. Emojis for a friend appear when the app has saved their key (after a claim), and the screen says they are the ones the app has saved. Until adding a friend exists (groups, #22), most listed friends show as "not saved yet"; the screen's work today is the list, "your emojis" and the review of a changed friend.
- **The review is captured (SEC-43).** `ContactsStateHolder.review` captures the pending observation and the emojis of the saved and the observed keys; the dialog renders only that. A refresh is ignored while a review is open. `trust` accepts exactly the observation the dialog showed; if the server changed it meanwhile, nothing is pinned, the review is rebuilt from the new observation with a visible note, and the confirmation tick is forgotten (a review version). From the second change on, trust is off for that review ("the key keeps changing").
- **The accept is typed (SEC-44).** `AcceptContact.reviewed` takes a `ReviewedObservation`, which only the holder can build, and is internal to `:shared`; `blindly` (dev CLI) needs the `@BlindAcceptForDevCli` opt-in; `DeviceAuth` hands the app an opaque `ContactsUseCases` bundle whose accept is internal. A text test still keeps the names out of the app modules.
- **The review is per reason (SEC-45).** A key conflict is explained and has no trust button. A rename or a reassigned name shows old and new names and words the button for what changes. A new phone or several phones shows every device, with "every one must be a phone your friend holds; if your friend has one phone, do not trust". The set that would be saved after trusting is shown, kept old pins included.
- **Wording (SEC-48).** "Trust the new key" and its siblings; the confirmation reads "I compared all 12 emojis and names with my friend, on a call or in person, not in a chat" (names only where glyphs are missing). The app never says verified, safe or secure.
- **Glyphs (SEC-47).** Names are visible text under every emoji. The notice "compare the names" stays up unless the platform says every glyph is drawn (Android `Paint.hasGlyph`; the web cannot tell). A missing glyph does not disable trust: the names are unique, so the comparison still works.
- **Cost (SEC-46).** One restore of the MLS client per screen update computes all needed fingerprints; the user's own emojis come from the local identity and are kept in the holder only while the screen is open.
- **Display (SEC-49).** No account id is shown, nothing offers to copy or share the emojis, usernames are plain text, state is in memory only and dropped when the screen is left. No `FLAG_SECURE`: the content is public keys and names.

### Not decided here
How people who are not neighbours find each other and ask to connect, and whether the claim is then restricted to accepted contacts, is a separate issue, #147 (owner request, 2026-10-22). A non-neighbour first claimed by name is pinned at first sight with no neighbour context until it decides their trust.

## Consequences
- The server gains one read-only endpoint over existing tables and no stored data. The threat model lists the permanent tree edge and the contact book.
- The client gains a trust store whose failure modes matter more than its encoding; PR 2 tests each (corrupt record, cap, concurrent update, failed write).
- Key verification stays weak until #31 and M3: first contact is TOFU, and unblocking is only as good as the decision above.
