# ADR-0013: Client presentation layer, session handling and the server origin

- **Status:** accepted
- **Date:** 2026-10-21
- **Issue/PR:** #17 (PR 1, the foundation: this ADR, the session holder, the origin setting, the invite-link parser; later PRs: onboarding screens, create-invite screen, App Links). Round-0 plan review on the first #17 PR (SEC-1 to SEC-13). Owner decisions in chat, 2026-10-21 (answers to my questions): presentation "AndroidX ViewModel + Navigation", origin "Editable in the app", App Links "Include now", split "Three PRs (Recommended)" (the plan review made it four: App Links last); plan "Go ahead (Recommended)"; lockfiles "You, on your laptop (Recommended)".

## Context
Onboarding (#17) is the first real UI. The project has use cases (`:shared` domain) and a placeholder `App`, but no presentation layer, no navigation, no logged-in session holder and no way to choose the server. The server is untrusted (ADR-0009): the origin the app signs for and talks to must be the app's own choice, never a value from the server or a link. Sessions last 24 hours without refresh (ADR-0009). Invite codes are one-use credentials (ADR-0010).

## Options considered
**Presentation.** (1) Plain state holders plus a hand-written navigation state: no new dependencies. (2) **AndroidX `ViewModel` and Navigation** (JetBrains KMP artifacts): standard, saved-state aware, two new dependencies. Chosen by the owner: (2).
**Server origin.** (1) A build-time constant only. (2) **Editable in the app** (owner's choice): more surface for look-alike servers.
**Session.** (1) Log in before every call (the CLI's way). (2) **One holder per app instance**, login on demand.

## Decision
- **Layers.** Presentation classes (UI state, event handling) are plain Kotlin state holders in `:shared` that take a `CoroutineScope`: testable on the JVM with fakes, and no androidx on the classpath of `:cli`, `:e2e`, `:mls` or the server. The `androidx.lifecycle` `ViewModel` wrapper and `navigation-compose` live in `composeApp` only (added with the first UI PR, with the owner-regenerated lockfiles and a one-line justification per artifact, rule 9). Screens render state and send events. **The invite code is never a route, a route argument, a `SavedStateHandle` or `rememberSaveable` value, or any saved state**: no `navDeepLink`; the platform entry point passes the code in memory to the state holder (`InviteCode`, whose `toString` is fixed text) and clears the intent or address-bar fragment.
- **`SessionHolder`** (`:shared`): the session in memory only; single-flight login in the holder's own scope; a renewal margin of 120 s; one repeat after a `401` with a new login, and no repeat of anything else (a timeout may have changed state); a failed login is returned, never repeated, and never touches storage (#73 SEC-42); `clear()` after wipe, logout or an origin change. After a wipe the next call answers `NOT_REGISTERED` from the login. When messaging exists (#21), the holder should sign with the app's live client instead of restoring a second one from the snapshot; a successful restore resets the counter (`GuardedMlsFactory`), so daily re-logins cannot add up to `RESTORE_BLOCKED`.
- **`ServerOriginSetting`**: the build supplies the default; the user may change it in Settings only, never from a link or an intent. An identity (pending, registered or unreadable) decides the origin and blocks changes; the setting only applies without one, and a lost setting never causes `OTHER_ORIGIN`. A change accepts only a canonical `https` origin after trimming and lowercasing, runs under the `DeviceLock` and re-checks the identity inside it; the caller rebuilds API, `DeviceAuth` and the holder afterwards. The wipe's `deleteAll` removes the record (back to the default). Release builds show the canonical origin (ASCII, `xn--` as is) on the invite and register screens and a banner on every screen while it is not the default, and a first registration needs an explicit confirmation of the origin before any request.
- **`InviteLinks`**: one strict function, no URL library: after trimming ASCII whitespace the whole string matches `^(canonical origin)/invite#(22 base64url)$`, the origin equals the configured one (another origin is "not for this server", never a switch) and the code is canonical. The link the app shows or shares is built from the configured origin and the code, never taken from the server's `link` unless it passes the same function. A just-created invite whose `link` fails it is revoked, best effort, and reported as a malformed answer, so it is never shown and doesn't hold one of the 5 open slots; it still counts toward the 20 a day, so a server whose public URL doesn't match the app's origin locks invite creation for a day after 20 attempts (`CreateInvite`, #17 PR 3a).
- **`OnboardingStateHolder`** (`:shared/presentation`, #17 PR 2a): the onboarding flow as a state machine the screens only render: invite, username, an explicit server confirmation, register, first KeyPackages. Nothing leaves the device and no key is made before `confirmRegistration`, which only acts from the confirmation state (so the confirmation gates the use case, not only the screen); username checks are local only; the invite code lives in the holder's memory and is dropped when the registration ended (kept only after a taken username, which leaves the invite unused). After any unclear registration the stored pending identity decides the next state (`FinishPending`): `RegisterDevice.resume()` finishes it without asking for the code, sending a syntactically valid placeholder that is not a real invite (the server answers a same-key retry as a login before it looks at the invite, ADR-0009 step 4; if the first attempt never arrived, the placeholder is refused and the identity stays for the user), and `discardPending` needs the screen's irreversible-action confirmation.
- **Dependencies (#17 PR 2b), `composeApp` and `androidApp` only:** `org.jetbrains.androidx.navigation:navigation-compose` 2.9.2 (latest stable; string routes, no deep links, no route arguments), `org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose` 2.11.0 (latest stable; on Android it moves AndroidX lifecycle up from 2.9.x), `io.ktor:ktor-client-js` (web engine) and `io.ktor:ktor-client-android` (Android engine, `HttpURLConnection`, no OkHttp), both at the project's Ktor version; neither follows redirects (`GifItUpApi` turns them off; the Android engine sets `instanceFollowRedirects = false` and `useCaches = false`, the web engine maps it to fetch `redirect: "manual"`). The build's default origin is a Gradle property (`gifitup.defaultOrigin`, checked canonical at build time; the placeholder `https://gifitup.invalid` reaches no server), generated into `BuildDefaults`.
- **Screens and wiring (#17 PR 2b):** everything bound to one origin (HTTP engine, API, `DeviceAuth`, `SessionHolder`) belongs to the onboarding `ViewModel` keyed by that origin and is closed in `onCleared`, so a rotation keeps it and nothing outlives it. An invite link from the platform's entry point goes through an `InviteInbox` that hands it over once and drops it on an origin change. Settings is the only place the origin changes, through its own state holder.
- **`CreateInviteStateHolder`** (`:shared/presentation`, #17 PR 3b): the create-invite screen as a state holder. One action at a time; every call goes through `SessionHolder.withSessionResult` (the same rules as `withSession`, for use cases that answer with `AuthResult`: one repeat after a `401` of the call itself, never after the login's, nothing else repeated). Create is never repeated on its own and a failed create always refreshes the list, because a lost answer may have created an invite the user never saw (it shows as open and can be revoked). The new link is in the state only until another invite, a revoke, or `leave()`; a create that finished after the screen was left drops its answer. The holder's `toString` classes leave the link out. Copying goes through `SensitiveClipboard` (the platform marks the entry sensitive where it can, `clearCopied` removes it without reading the clipboard); it is cleared when the link is dropped. The platform parts: `AppGraph.clipboard` (Android: the application context only, never an Activity, marked sensitive from Android 13; web: `navigator.clipboard`, which can neither mark nor clear, so `clearsCopied` is false and the screen says so) and `ScreenProtection`, handed to `App` by the Activity (`FLAG_SECURE`) and used only inside the composition. The screen is a second destination over the onboarding ViewModel of the same origin (`getBackStackEntry`), so it shares the API, the engine and the session and they close together (#131 SEC-23). It calls `leave()` when it is disposed, `stopped()` when the lifecycle stops and `resumed()` when it starts: the link leaves the screen and memory but the clipboard entry is kept, because the user is on the way to paste it (clearing it then would also be refused from Android 10). A `leave()` between `stopped()` and `resumed()` (a rotation rebuilds the screen) keeps it too; the next deliberate leave, a new invite, or the revoke of that invite (the holder remembers which invite is on the clipboard) removes it, best effort. The link text isn't selectable, so only the Copy button writes the sensitive, labelled entry.
- **Android App Links** (#17 PR 4): one intent filter, `https://<host>/invite`, `autoVerify`, `BROWSABLE`; no `navDeepLink`. The host is a manifest placeholder from the build's default origin (never committed). The verification file is served by Caddy (`deploy/caddy/gifitup.caddy`, `docs/ops/deploy.md`). The launch intent is untrusted: `MainActivity` reads it once (`LaunchLink.candidate`: a VIEW, at a fresh launch, `https`, bounded; the strict `InviteLinks.parse` decides after that), hands it to the `InviteInbox` and replaces the activity's intent before the NavHost exists, so Navigation never sees its extras (#131 SEC-21). A build check allows exactly two intent filters, the launcher and this link.
- **Not decided here:** the web `/invite` route's hosting and CSP (#27).

## Consequences
- Presentation tests need no UI; the screens stay thin. The two androidx libraries and their transitive dependencies enter only `composeApp`, and the owner regenerates the lockfiles and checksums (the cloud session cannot).
- An editable origin lets a user point the app at a look-alike server; mitigations are above and in the threat model. A signature is bound to the app's own origin, so a look-alike cannot replay a registration or login at the real server.
- Metadata: none new on the server (the origin is a local setting).
