# ADR-0011: Client storage

- **Status:** accepted
- **Date:** 2026-10-18
- **Issue/PR:** #16 (PR A: this ADR, the `:shared` seams and use cases; PR B: web; PR C: Android). Round-0 plan review on the first #16 PR (SEC-1 to SEC-12). Owner decisions in chat, 2026-10-18: "No passphrase in v1 (Recommended)"; "Move them out (Recommended)" (the items that need messaging go to #21, #22, #24); plan approved: "i approve".

## Context
The app has to keep its identity across restarts: what it registered as (origin, username, device id), the MLS snapshot, and the 32-byte key that snapshot is encrypted with. The snapshot is already encrypted inside Rust (ADR-0007), but its key arrives as raw bytes, and a non-extractable platform key can't hand out raw bytes. The `:shared` use cases already persist through two seams, `IdentityStore` and `SnapshotKeyStore` (#95), which the dev CLI implements with plain files for test accounts.

Constraints: no hand-rolled cryptography (CLAUDE.md); key code stays in `crypto/` and `:mls`; the web has no real at-rest protection without a user secret (ADR-0002); a web panic is a trap that reloads the page (ADR-0007).

## Options considered
1. **Store the raw snapshot key next to the snapshot**: simple; anyone who reads the app's storage has everything. Rejected.
2. **A user passphrase on every platform**: real protection on the web, proportional to its strength; friction on every start, and a lost passphrase loses the account. Rejected for v1 (owner decision).
3. **Envelope encryption with a platform key**: a non-extractable AES-256-GCM key in the Android Keystore or WebCrypto wraps a random data key, which is the snapshot key. Strong on Android, honest about the web, and a passphrase can be added later as a second wrap. **Chosen.**

## Decision
- **Envelope.** The snapshot key is 32 random bytes from the platform CSPRNG (`SecureRandomSource`), generated once per identity. It is stored only wrapped: `version(1) || iv(12) || AES-GCM ciphertext and 128-bit tag`, with AAD `"gifitup snapshot key v1" || 0x00 || version || canonical origin`. The version is authenticated, and a wrapped key can't move to another origin's slot. The origin comes from the configured endpoint. Unwrap checks the exact length, the version and a 32-byte result, and zeroes the plaintext on every error path; a tag that doesn't verify (another key, changed bytes) is `KEY_UNAVAILABLE`, since the two can't be told apart. The format and AAD live in `:mls` (the key module), tested on the JVM with real `javax.crypto` AES-GCM; `:shared` sees opaque bytes only.
- **Wrapping key.** Android: an Android Keystore AES-256-GCM key (encrypt/decrypt, randomized encryption), StrongBox when `SDK_INT >= 28` and available, otherwise TEE; no user-authentication requirement in v1, and `setUnlockedDeviceRequired` is rejected for now (it conflicts with background sync). Web: `crypto.subtle.generateKey` AES-GCM 256 with `extractable = false`, the `CryptoKey` kept in IndexedDB. The wrapping key is created **only** when a key is saved and no wrapped key exists; loading never creates one. A missing or invalidated wrapping key is the typed error `KEY_UNAVAILABLE`, never a fresh key, and `save` refuses any key while a registered identity exists. `save` checks what `load` will check before it writes: the sealed size, and that the sealed key opens to the same key; a mismatch is `STORAGE` and writes nothing.
- **Stores.** One `LocalStore` per device: a key-value store whose `putAll` is atomic and durable when it returns. Android: one file in `Context.noBackupFilesDir`, written temp → fsync → rename → fsync dir; the existing `allowBackup=false`, `fullBackupContent=false` and `data_extraction_rules.xml` stay. Web: one IndexedDB database, each `putAll` one `readwrite` transaction with `durability: "strict"`, resolved on `complete`, and aborted as a whole if queueing any entry throws; `requestPersistentStorage` calls `navigator.storage.persist()` and records the answer, and onboarding (#17) calls it at registration (not at start: Firefox asks the user). `RecordIdentityStore` and `StoredRestoreCounter` (`:shared`) store the identity record (a strict, versioned binary encoding) and the restore counter in it.
- **Writes.** Key, then identity: two writes, each atomic and durable, as `RegisterDevice` already orders them; a crash in between leaves an orphan wrapped key, which the next registration replaces. `putAll` takes several entries, so #24 can later write the snapshot and an outgoing message's bytes in one transaction.
- **One active instance per device.** Registration, discard, login and wipe share one `DeviceLock`, so they never overlap within an instance (#108 SEC-15); the platform makes sure only one instance uses the store. Web: an exclusive Web Locks lock (`navigator.locks.request("gifitup-device", {mode: "exclusive", ifAvailable: true})`) held for the page's lifetime; a tab that doesn't get it opens no storage and says the app is open in another tab; the database connection closes on `versionchange`. Android: the stores and use cases are built once per process (an `Application` subclass), not per Activity.
- **Restore guard.** `GuardedMlsFactory` is the only way the use cases restore a client. It counts each restore in the store before it starts and clears the count when the restore returns a client or fails with a typed error other than `Poisoned`; restores run one at a time. A trap counts: on the web it comes back as `MlsException(Poisoned)` on the call that trapped, or the page dies, and on Android the known panic in restore is `Poisoned` too (#108 SEC-21). After any `Poisoned` the app reloads the web page or drops the Android client before restoring again, so a module that was already dead doesn't spend a good snapshot's attempts (#17). After three counted restores it refuses (`RESTORE_BLOCKED`) until the user chooses "try again" or a reset. A failed unwrap is `KEY_UNAVAILABLE` and never counts, and a store failure is `STORAGE_FAILED`, a closed error that zeroes the key first (#108 SEC-13). The reset needs an explicit confirmation that it is irreversible (#17).
- **Wipe.** `WipeLocalData`: best-effort logout, close every live client, destroy the wrapping key, then delete the records and the store; the web app then reloads. Both steps are idempotent, so a wipe that stopped part-way completes when run again; the app offers it again from a lasting `KEY_UNAVAILABLE` (#17, #108 SEC-18). It doesn't delete the account on the server (ADR-0010).
- **No passphrase in v1** (owner decision). Revisit when the web client holds group secrets worth more than the account (M2), or on the owner's request; an optional passphrase is its own `later` issue.

## Consequences
- **What it protects.** Android: a reader of the app's files (a backup, a forensic copy of the files, another app through a platform bug) gets only wrapped bytes; the wrapping key never leaves the Keystore. Not protected: code running as the app's uid (including `adb run-as` on a debuggable build, so release builds stay non-debuggable), a rooted unlocked device that can call the Keystore, and memory (the snapshot key is in the heap while the app runs). Web: nothing against a copy of the browser profile (Chromium and Firefox store the `CryptoKey`'s raw bytes in it) or script in our origin; an accepted risk, signed off by the owner in chat on 2026-10-19 (threat model).
- **Old copies.** "No old snapshots" holds for the app's logical store: one record, replaced in place. Physical copies are not erased: Chromium's LevelDB files, Firefox's SQLite WAL and free pages, and flash wear-levelling can keep old encrypted snapshots for a while, all under the same data key. A discard or a refused registration removes only the wrapped key, and the next registration reuses the wrapping key, so leftover copies of an orphaned account's wrapped key still open for anyone who can use the wrapping key (who gains nothing new by it). On Android, destroying the Keystore key is what makes them unreadable; on the web the wipe is best effort.
- **Eviction (web).** IndexedDB is best-effort storage unless the browser grants `navigator.storage.persist()`. A granted origin isn't evicted under storage pressure, but browsers decide the grant by their own heuristics and may refuse it; the app records the answer (`storage-persisted`). Safari deletes script-writable storage after seven days without use outside home-screen apps, and how that interacts with `persist()` isn't documented (#108 SEC-19). Eviction loses the identity (a new invite; the old username stays with the orphaned account). One more reason the Android app is the stronger client.
- **Data-key lifetime.** The data key lives as long as the identity: `MlsClient` takes it once and has no rekey (ADR-0007, amended). Exports are rare until messaging: today at most two per registration attempt. The export bound and the rekey path arrive with #22, before exports become per message.
- **Moved out** (owner decision 2): persist before send and ack, freshness against the Delivery Service and its label, and persisting outgoing message bytes atomically go to #21, #22 and #24; a local database for app data gets its own issue; nothing in this ADR claims them.
- **Testing.** The `:shared` logic and the wrapped-key format run on the JVM; the web store and WebCrypto run in headless Chrome in CI; the Android Keystore needs a device, so it is checked by hand on the owner's phone (no emulator in CI).
