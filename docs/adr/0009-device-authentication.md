# ADR-0009: Device authentication

- **Status:** accepted
- **Date:** 2026-10-16
- **Issue/PR:** #12 (PR C: this ADR and the crate's signing function; PR D: the endpoints). Round-0 plan review on #68 (SEC-1, SEC-2, SEC-3, SEC-6, SEC-7, SEC-9, SEC-11, SEC-12, SEC-14).

## Context
Every API call except `/health` must be authenticated (#12). The server is untrusted (CLAUDE.md), the app has no passwords by design, and a device already holds a long-term key: its Ed25519 MLS signature key, which lives only inside the crate (ADR-0007). Accounts are created with an invite (#13); a lost device means a new invite and a new account, because device linking is deferred to its own issue (owner decision, 2026-10-16).

Constraints:
- **The shared `proxy` network** (ADR-0005): any container on it can reach the server directly, forge headers, and register the server's alias to receive part of its traffic after TLS.
- **The crypto boundary:** key material stays in `crypto/`; Kotlin never sees a private key and must not be able to sign arbitrary bytes.
- **No passwords, no new dependency on the server.**

## Options considered
**Which key signs** (owner decision, 2026-10-16):
1. **The MLS signature key** (chosen). One key per device. The server stores its public key, so #14 can check that a device's KeyPackages carry the registered key. Needs domain separation from MLS signatures.
2. **A separate auth key** generated in the crate and stored in the snapshot. Clean separation, but more crate code, and the server can't link KeyPackages to the registered device.

**How a session is proven:**
1. **Signed challenge → short-lived bearer token** (chosen). One signature per login, then a cheap token check per request.
2. **Signing every request.** No bearer token to steal, but every request needs a crate call and canonical request encoding, and WebSockets (#21) don't fit.

## Decision

### The signature (in place with PR C)
`NativeMlsClient.sign_auth(purpose, challenge, origin, subject)` in `crypto/src/auth.rs`, exposed as `MlsClient.signAuth` (both bindings, contract-tested on the JVM and in headless Chrome). The crate builds the signed bytes itself from typed parameters; **no FFI function signs arbitrary bytes**. Two checks in `scripts/check-repo-hygiene.sh`: no function with a `sign` name segment other than `sign_auth` in the binding files (generics included), and neither `wasm_bindgen` nor `uniffi::export` (any spacing, `cfg_attr` included) outside the two binding files (#70 SEC-24, SEC-27). They are text checks of the usual spellings: an export under a name without `sign`, or one reached through a macro or alias, is left to review.

The signed bytes use MLS `SignWithLabel` framing (RFC 9420 §5.1.2) with our own label. `<V>` is the MLS variable-length vector with a minimal RFC 9000 varint length prefix (RFC 9420 §2.1.2):

```text
struct {
    opaque label<V>   = "MLS 1.0 GifItUp auth v1";
    opaque content<V> = AuthContent;
} SignContent;

struct {
    uint8  purpose;       // 1 = register, 2 = login; a closed set
    opaque challenge<V>;  // the server's challenge, opaque to the client, 16..64 bytes
    opaque origin<V>;     // the client's own configured origin, canonical form
    opaque subject<V>;    // register: the client's username; login: the device id
} AuthContent;
```

- **Domain separation:** every MLS signature uses a label `"MLS 1.0 " + <MLS label>`, and no MLS label is `GifItUp auth v1`. So an auth signature is never a valid MLS signature and the other way round. The signature is pure Ed25519 over `SignContent`, like every MLS signature with this ciphersuite.
- **Rules the crate enforces** (each tested; violations are `InvalidInput`):
  - **challenge:** 16 to 64 bytes. The server defines its layout (PR D).
  - **origin:** canonical only: `https://`, a lowercase host (letters, digits, `-`, `.`; no empty labels, no leading or trailing `-`), an optional port 1..65535 without leading zeros and never 443, nothing after it, at most 256 bytes. One origin has exactly one accepted spelling, so client and server always sign and verify the same bytes. **The client passes the origin it is configured with, never one the server sent** (#17).
  - **subject:** for register, exactly this client's own username, so the server can't get a registration signature for another name. For login, a lowercase canonical UUID (the server-assigned device id).
  - **purpose:** a closed enum (uniffi) or exactly `"register"`/`"login"` (web; a string because wasm-bindgen truncates JS numbers to the parameter's integer width, #70 CR-1, SEC-26); anything else is refused.
- **Test vectors:** `server/src/test/resources/auth-signature-vectors.json`, generated by the crate from the RFC 8032 §7.1 TEST 1 key. The crate's test fails if its output differs from the committed file; PR D's server verifier checks the same file, so both sides are pinned to the same bytes. The vectors were also verified independently with the JDK's Ed25519 (`X509EncodedKeySpec` with the fixed SPKI prefix), and a one-byte change to the signed bytes fails each of them. One vector has a 64-byte challenge, whose length needs a 2-byte varint.

### The protocol (in place since #12 PR D2)
In `server/.../auth/`: `AuthService` (the use cases, HTTP-agnostic), `AuthRoutes` (endpoints and the session interceptor), built on the D1 blocks: `authSignContent` with a typed `AuthSubject` and `CanonicalOrigin`, `SignatureVerifier`, `Challenges`, `KeyedRateLimiter`, `UsernamePolicy` and the repositories. Registration needs a valid invite (`DbInviteRedeemer`, ADR-0010, since #13).

Endpoints (all JSON, `ProtocolJson`, closed errors per ADR-0006):
- `POST /auth/challenge` → a **stateless** challenge: `random[16] ‖ issuedAt ‖ HMAC-SHA256(serverKey, random ‖ issuedAt)`, with a key generated at server start. No state is stored per challenge, so flooding this endpoint costs the attacker as much as the server (round-0 SEC-1).
- `POST /accounts {username, inviteCode, signaturePublicKey, challenge, signature}` registers an account and its first device. Fixed order (SEC-3), so that a taken username can't be probed without a valid invite:
  1. input format (400);
  2. the username rule (400) and reserved names (409; the list is public, so this reveals nothing);
  3. the challenge's MAC and age, and it is used up right there (401 if stale, forged or already used), then the global budget (429), then the signature over `subject = username` with the submitted key (401);
  4. in one transaction: if this key is already registered **under this username**, the request is a retry whose reply was lost, and it gets a new session for that device (#73 CR-1, owner decision 2026-10-16; the signature over a fresh challenge proves key possession, so this is a login and needs no invite; the per-device budget applies). The same key under another username is a 400;
  5. otherwise: invite redemption (403), the account insert (`409` only after a valid invite, rolled back so the invite stays unused), device and session.
- **Client rule for a lost reply** (#73 CR-6): after a register whose outcome is unknown (timeout, dropped connection), retry with the same key and username. A `403` or `409` on that retry can be transient (the first attempt may still be committing), so retry once more after a few seconds before treating it as final. Even then, a refused retry never discards the key automatically: the lost attempt may still commit, so only the user discards it (#95 CR-5, SEC-6; `RegisterDevice.discardPending`). In #17's checklist.
- **Two ways to get a session** (#73 SEC-40): login and the register retry both issue sessions. Any future check (device revocation in #72, disabled accounts) goes into one helper both paths call.
- `POST /auth/login {deviceId, challenge, signature}` → a session token. Order: input format (400), challenge checked and used up, global budget (429), the device exists, signature, then the per-device budget (429; only a caller whose signature checked out can see it, #73 SEC-36). An unknown device, a bad signature and a stale or reused challenge all get the same `401 {"error":"unauthorized"}`.
- `POST /auth/logout`, `GET /devices` (own devices only, account from the session).

Verification and sessions:
- **Expected origin** (#70 SEC-25): the verifier rebuilds the signed bytes with the server's **own configured** public origin, never with one taken from the request (`Host`, `X-Forwarded-Host`, `Origin`). The origin is read once at startup and must pass the same canonical rule as the crate's `is_canonical_origin`, or the server refuses to start; a test checks that a request with a different `Host` header still verifies against the configured origin only. Without that, a relaying server at another origin could have its signatures accepted. (The looser `GIFITUP_PUBLIC_URL` regex in `deploy.sh` only gates the health check.)
- **Verifier:** the JDK's `Ed25519` with the key wrapped as `X509EncodedKeySpec(302a300506032b6570032100 ‖ key)`, so no point decoding is hand-written (SEC-9). Keys are decoded at registration (failure → 400), small-order keys are rejected, `GeneralSecurityException` maps to 400 or 401, never 500.
- **Challenges are single-use:** a request with a fresh, genuine challenge uses it up immediately, before the shared budget and the signature check, so each challenge can be tried exactly once and a replay fails at one set lookup (#73 CR-7, SEC-39; first planned as "only after a valid signature", which let one challenge be replayed for its whole lifetime). The used set is bounded by the challenge rate limit times the TTL (about 6.5k entries) and refuses rather than forgets when full (SEC-1).
- **Rate limits** never key on an IP (SEC-M0-5):
  - Global buckets protect the CPU: one for `/auth/challenge` (100/s, burst 200) and one for login and register (50/s, burst 100). The login/register bucket is spent only after the input format and a fresh, genuine challenge check out, so forged or stale challenges cost nothing shared (#73 SEC-34).
  - A per-device bucket (10 logins per hour) is spent on **success** only, so failed attempts by someone else can't lock a device out (SEC-2), and it exists only for real devices, so random ids can't fill the limiter (#71 SEC-30). No per-invite limit: invite codes are 128-bit and a redemption uses the invite up (ADR-0010).
  - **A per-account request budget** (#76) covers every authenticated request: burst 120, then 4/s, one bucket per account, shared by all its sessions and devices. It is checked in the session interceptor right after the session lookup, before routing, so a new endpoint is covered without opting in; over it, `429 rate_limited` and the route doesn't run. Endpoints with tighter limits of their own keep them (invite creation, ADR-0010).
    - **What it doesn't cover:** it counts HTTP requests, including a WebSocket upgrade, but not WebSocket frames; frame and message limits belong to the messaging issue (#21). The buckets are in memory, per server process, and reset on restart.
    - **Exempt:** the calls that end a session or revoke a device, each as an exact method plus a whole-path pattern (#77 SEC-70, SEC-71): `POST /auth/logout` today, `DELETE /devices/{id}` when it comes (#72). Any other method on those paths spends the budget. Otherwise one session draining the budget (say, a stolen one) would also block those calls (#76 SEC-65). Today that only keeps logout working for every device: logout ends the calling session only, so a stolen session can't be ended through the API until device revocation (#72); until then, the runbook or its 24 h expiry ends it (#77 CR-2). Future revocation routes must join the exemption.
    - **Cost of a throttled request:** the session lookup still runs first (the account is only known after it): one indexed read plus the `last_seen` update, which matches no row unless the stored time is over an hour old (#76 SEC-67).
    - **Fails closed:** if the limiter can't create a bucket, the request is refused (#76 SEC-69).
- **Sessions:** a 256-bit random token, sent as `Authorization: Bearer`. The database stores its SHA-256 (ADR-0008). Each token expires 24 h after it's issued, with no refresh: the device always holds its key and simply logs in again. At most 5 sessions per device, oldest evicted. Expiry is checked in the lookup query, so expired rows are only cleanup.
- **Deny by default** (SEC-6): an interceptor directly after the protocol version check requires exactly one `Authorization: Bearer <token>` with a live session on every path except `/health`, `/auth/challenge`, `/auth/login` and `/accounts`, before routing runs. A new route is protected without opting in, and an unknown path answers 401, not 404, to a caller without a session, so nobody can map the API without logging in. (Planned with Ktor's `Authentication` plugin; an interceptor needs no new dependency and makes a route-walk test unnecessary.) The token is never logged.

## Consequences
**What it protects against:**
- **A different server:** a signature made for one origin doesn't verify for another, because the client signs its own configured origin.
- **Replay:** a challenge expires and is single-use.
- **Cross-use:** a registration signature can't log in and the other way round (purpose), and no auth signature is an MLS signature or the reverse (label).
- **A stolen database:** it holds only public keys and token hashes.

**What it does not protect against (stated in the threat model):**
- **A man in the middle after TLS** on the shared `proxy` network (ADR-0005, accepted risk). A peer that takes the server's alias relays the real challenge and keeps the session token, so it gets a valid token for up to 24 h. There is no channel binding. This is the reason for short sessions.
- **The global unauthenticated buckets are a lockout lever** (accepted risk, owner decision 2026-10-16, #73 SEC-34): anyone can spend them and slow down every friend's login. The per-key limits and the cheap stateless challenge keep the cost of that low, not zero.
- **Device ids are not secret.** Group members will see them (#22), so login must never rely on their secrecy; it relies on the signature.
- **Key compromise:** auth key = MLS key, so a stolen, unlocked device gives both, and MLS post-compromise security does not cover a stolen signature key.
  - **Rotation:** there is no key-rotation endpoint yet. Rotating the MLS signature key would break login and #14's KeyPackage check, so it needs its own "key change" step later.
  - **Revocation:** there is no self-service device removal before the device-linking issue (`DELETE /devices/{id}`). Until then, the owner deletes a device by hand (`docs/ops/deploy.md`, runbook).
- **#14 must check both:** the KeyPackage's BasicCredential identity equals the account's username **and** its signature key equals the registered key (#14's body). Done at upload by the server's KeyPackage reader (ADR-0012), against the session's device.
- **Metadata:** the server sees which device logs in when, and how often, which it already does through every request.
