# ADR-0017: Message history store

- **Status:** accepted as the design. **Built so far: the sealing in `crypto/` and its bindings (PR 1), and the store logic over a record-store port, `EncryptedMessageStore` with retention and a plain record codec, tested with the real cipher (PR 2a), the read marks as sealed records (PR 2b), and the history key with its wrapping and migration rule (PR 2c).** Everything marked *planned* below (the platform record stores, the failure behavior of the sync engine, the wipe, "reset history", the app wiring, the CLI command) is a requirement on the later PRs and doesn't exist yet; each of those PRs updates this ADR and the threat model as it lands
- **Date:** 2026-10-29
- **Issue/PR:** #177. Round-0 plan review by the security reviewer (SEC-1 to SEC-12, all folded in below). Owner decisions in chat: 2026-10-27 "Separate encrypted store" (ADR-0011); 2026-10-29, on the web: "Accept it, shorter on web (Recommended)" (the web's accepted at-rest risk extends to the message history, 200 messages per group on the web, 1000 on Android); 2026-10-29, on the plan: "Approve, start PR 1 (Recommended)".

## Context
Decrypted messages (GIF links, captions, group names) are plaintext. ADR-0011 keeps them out of the `LocalStore` (which holds nothing that isn't encrypted or public), and #24 keeps them behind the `MessageStore` port in memory only, so history ends with the process. Before the friends alpha (#27) a conversation has to survive a restart. Constraints: the crypto boundary (all key and ciphertext code lives in `crypto/`, CLAUDE.md), no new dependency, nothing about messages reaches the server (no server or wire change), the web has no at-rest protection against a profile copy or script in our origin (ADR-0011), and the snapshot key is rotated by `rekeyAndExport` (ADR-0016).

## Options considered
1. **Messages in the MLS snapshot's `app_state`**: capped at 256 KiB and rewritten with every export. Rejected.
2. **One sealed blob per group, rewritten on every insert**: simplest and hides the per-group message count, but rewrites up to ~1 MB per insert in IndexedDB. Rejected for cost; the fallback if per-record listing proves slow.
3. **A history key derived from the snapshot key (HKDF)**: orphaned by `rekeyAndExport` (every record would need re-sealing). Rejected.
4. **SQLite/SQLDelight (#109)**: a new dependency, web support unproven. Rejected for v1.
5. **Sealing in Kotlin (JCA, WebCrypto)**: breaks the crypto boundary. Rejected.
6. **A separate random history key, sealing in the crate, one sealed record per message, record names hidden by a keyed PRF.** **Chosen.**

## Decision
- **The cipher (this PR, `crypto/src/history.rs`).** `HistoryCipher` is its own crate object, separate from `MlsClient` (its lifetime and failures don't depend on the group state; a restore that is blocked or poisoned doesn't make the history unreadable), reached through `NativeHistoryCipher` (uniffi, wasm-bindgen) and the `HistoryCipher` interface in `:shared`. It holds one random 32-byte **history key** and the account's canonical origin. Two sub-keys come from HKDF-Expand (SHA-256) of the history key with labels `"gifitup history seal v1"` and `"gifitup history name v1"`.
- **Record names.** `HMAC-SHA-256(name_key, kind ‖ u32-BE len ‖ group id [‖ u32-BE len ‖ message reference])`, kind `g` (the group's folder), `m` (a message), `r` (the read mark). The store sees only these 32 bytes: without the key they say nothing about the group id or the message reference (ADR-0006 B9 treats the reference as content, not as something the server holds), and a disk reader who also holds the server's ciphertext can't match a record to it by name or content (counts, write times and bucket sizes still correlate with the server's arrival times, see *Consequences*). The crate takes only ids from the caller and builds names itself (SEC-8).
- **Sealed record.** `"GIUH" ‖ version(1) ‖ nonce[12] ‖ AES-256-GCM(padded)`, associated data `header ‖ "gifitup history v1" ‖ 0x00 ‖ origin ‖ 0x00 ‖ record name`: a record can't move to another name, group or origin and its version can't be swapped. The AEAD is the OpenMLS crypto provider's (as for the snapshot, nothing hand-rolled), a fresh random nonce per seal. `padded` is `u32-BE length ‖ plaintext ‖ zeros` up to a multiple of 1 KiB (at most four buckets, 4092 bytes of plaintext), so a record's size only tells its bucket, not the caption's length (SEC-6). Sizes are checked before decryption; the inner layout is read only after the tag verified, and padding that isn't zeros is refused. Typed errors: `HistoryInvalid` (a size, header or layout no seal makes), `HistoryAuth` (another key, name or origin, or a changed byte). Random-nonce bound: every seal counts, a rewrite for a new delivery state too, 2^32 under one key (NIST SP 800-38D); no history comes near it and no counter is kept (SEC-12).
- **The history key (built, PR 2c).** A separate random 32-byte key from the platform CSPRNG, **not** derived from the snapshot key. `HistoryKeyStore` (port in `:shared`) and `EnvelopeHistoryKeyStore` (`:mls`) keep it wrapped with ADR-0011's envelope in its own entry `wrapped-history-key`, AAD label `"gifitup history key v1"` (version and canonical origin bound in): the two wrapped keys have the same size and share one wrapping key and origin, so the label is the only thing that keeps one from opening as the other (tested both ways). The history key's `save` never makes a wrapping key (so it can never be the reason a fresh one orphans the snapshot key), never replaces a stored key, and checks that the sealed key round-trips. **`OpenHistoryKey`** (use case on `DeviceStorage`, under the storage's own `DeviceLock` also on the load path, only for a registered identity of the configured origin) returns the stored key, or makes one **only when the record store positively holds nothing** (`RecordStore.isEmpty()`: no folder, no record, malformed or foreign names included; a listing error is `STORAGE`, never "empty"); a stored key that doesn't open or is damaged, or history without a key, is `KEY_UNAVAILABLE`/`DAMAGED` and **never** makes a fresh key (a transient error must not orphan the history). **A new identity gets its key lazily by this rule, not in the same `putAll` as registration** (no records exist then, so it is equivalent, and the registration transaction stays unchanged); registering a new identity also clears any leftover history store and `wrapped-history-key` (PR 4). The platform record stores must pass a contract test that a store holding only a malformed or temporary entry does not read as empty (PR 3). **"Reset history"** (PR 4, separate from the identity wipe: history is not worth losing the account, SEC-3) works whether the key entry is present, absent or damaged and records are present or absent, in this order: delete the records, clear the key entry, then `OpenHistoryKey` makes a new key; a crash in between leaves records without a key, the same state again. It is logical deletion: remnants of the old wrapped history key can persist, and while the wrapping key exists (the web always, Android until the wipe) they still open remnant records. The adversary is a reader of the disk or browser profile, never the server.
- **The record store.** The port `RecordStore` in `:shared` (`put`, `get`, `list`, `delete`, `deleteFolder`, `folders`, `deleteAll`, names checked as 64 hex digits; built in PR 2a with an in-memory implementation), single-record atomic writes only; the platform implementations are **planned, PR 3**: Android one file per record under `noBackupFilesDir/gifitup/history/` (temp, fsync, rename, fsync the directory; `list` ignores and removes temp files), the web a second IndexedDB database `gifitup-history` (strict durability). Every name is checked against `^[0-9a-f]{64}/[0-9a-f]{64}$`-shaped ids before it touches storage, so no path can leave the folder (SEC-9). Registering a new identity clears any leftover history store (an interrupted wipe, another key). On the web the history store is best effort and a missing store next to a valid identity is normal, not an error: the history database can be evicted on its own (SEC-4, open point 4).
- **`EncryptedMessageStore` (built, PR 2a).** Implements `MessageStore`: `insert` is idempotent per (group, reference) and first-seen wins; `setState` rewrites one record; `messages(group)` lists the group's records and orders them by the arrival number inside the sealed record (the next number is the highest seen plus one, gaps allowed, ties broken by reference; SEC-7). Every record carries its group and reference sealed inside and they are checked on open. A record that fails to open is **counted, never shown, never deleted, never logged with content**; the store keeps the count (`unreadable(group)`); the UI states "history unreadable" (every record of a group fails under a key that should be valid) and "n messages unreadable" are **planned, PR 4** (SEC-10). A record store that can't be read while a group loads is a storage failure for that group and nothing is cached half loaded; `insert` answers `false` both for a message already stored and for a new group over the limit.
- **Retention (built, PR 2a).** Per group only: the oldest messages of that group go on insert. The store's default is 1000 per group (Android); **the web's 200 is the owner's decision of 2026-10-29 and is passed in where the web store is wired, PR 4**. At most 50 groups (as `InMemoryMessageStore`); a new group over the limit gets no records, and nothing ever evicts another group's history (a flooding member can only push out their own group's older messages; SEC-5). Eviction runs with the insert and is enforced again on the next one, so a crash leaves more records, never fewer.
- **Read marks (built, PR 2b).** One sealed record per group, in the group's folder under the cipher's `r` name: version byte and the reference of the newest message shown (33 bytes of plaintext). Unread is counted by position after that message in arrival order, so a message of the same second still counts; a mark naming a message that is gone (retention removes the oldest first), unreadable or never known means everything held is unread. `EncryptedMessageStore` is the `ReadMarkStore`: it writes a mark only for a group it holds and a message it holds, so a late write after `forget` cannot create a folder or get past the group limit, and a load neither shows, counts nor evicts the mark. `ReadMarks` keeps the value in memory, writes only on change, and a failing store only costs the mark across a restart. Nothing is wired into the app yet (PR 4).
- **Failure behavior on receive (planned, PR 2; SEC-1, the high finding).** The history write comes first, then `advance`, then the snapshot. A failed history write is **not** a silent loss and **not** a retry in the same client: `stageIncoming` has already used up that message's generation in the in-memory MLS client, so the sync engine must **discard that client and restore from the last persisted snapshot** before anything exports it again, and it must not export between the stage and the history write. The message then arrives again from the server and is reprocessed from the old snapshot (the idempotent insert absorbs a crash between history and snapshot). Test (a hard requirement of PR 2): the sink fails, another group syncs and persists, the app restarts, and the message is stored once. **An oversize or invalid record is not a transient failure (SEC-14):** content over the codec's cap (896 bytes, ADR-0006 B3) is already `Unavailable` before it is stored, so a stored record (sender, times, state, body) stays well under the 4092-byte limit of `seal`; a `HistoryInvalid` from `seal` is a defect, never retried as a storage failure, and the message is kept as `Unavailable` rather than blocking the group's receive. PR 2 tests this with a maximal message (longest slug and URL, a 120-code-point caption of 4-byte characters, the longest sender).
- **Failure behavior on send (planned, PR 2; SEC-2, SEC-11).** Order: the SENDING record first (a failed insert aborts the send before anything is posted), then the snapshot that holds the pending send **with the message reference** (`PendingSend` and its codec; the reference is verified against the payload on decode, older snapshots read as "no reference"), then the post. On start a SENDING record that isn't the group's pending reference becomes FAILED. A send is settled by its reference only; the "last SENDING message" lookup goes away.
- **Wipe (planned, PR 4).** `WipeLocalData` also deletes the history records (the wrapping key is destroyed first, as in ADR-0011: on Android that makes every leftover copy unreadable, on the web the wipe is best effort).
- **Dev CLI (planned, PR 4).** Keeps its unprotected files (test accounts only) and gets the same store over a file `RecordStore` and a `chat-history` command, so the end-to-end test can show that the history survives a restart.

## Consequences
- **What it protects.** Android: a reader of the app's files (a backup, a forensic copy, another app through a platform bug) gets sealed records with hidden names and bucketed sizes, and the wrapping key never leaves the Keystore. Not protected: code running as the app's uid, a rooted unlocked device that can call the Keystore, memory.
- **What it does not protect (SEC-4).** Web: nothing against a copy of the browser profile (Chromium and Firefox keep the `CryptoKey`'s raw bytes in it) or against script in our origin, which can open any record. This is the already accepted web at-rest risk, extended to the message history by the owner on 2026-10-29 (threat model); the web keeps fewer messages (200 per group) for that reason. Deleting is logical: evicted, forgotten or wiped records can remain as physical remnants (LevelDB, SQLite free pages, flash wear levelling), all openable with the one long-lived history key while the wrapping key exists; on Android destroying the wrapping key is what makes them unreadable, on the web it is best effort. Forward secrecy does not cover this store (threat model, limitations). Records can be deleted or rolled back (a SENDING record put over a SENT one) by anyone who can write the store, and the store does not detect it (it is unauthenticated at the set level, and a missing record looks like a message that never came): inside the model (local write access is game over; rollback is already a limitation).
- **Metadata a disk reader still learns:** how many records a group has (and so roughly how many messages), when they were written (file times) and in which size bucket, which a reader who also has the server's arrival times can correlate with them. Not the group id, the references, the senders, the times inside the messages, or the caption lengths.
- **One wasm module on the web (SEC-16):** the cipher and the MLS client share the module, so a trap in the MLS path marks it dead and the cipher fails with `Poisoned` until the page reloads. The app then shows "reload" (PR 2), never "history lost", and deletes nothing. On Android the cipher is independent of the MLS client's state.
- **The origin must be canonical (SEC-17):** the crate only checks 1 to 256 bytes; two spellings of the same origin would make every record fail with `HistoryAuth`, which looks like tampering. PR 2 uses the one canonical-origin function the rest of the app uses (ADR-0013) and tests it across platforms.
- **The key must be uniformly random (SEC-18):** HKDF-Expand without Extract is right only for that, and the crate accepts any 32 bytes. The key comes from the platform CSPRNG (`SecureRandomSource`, as the snapshot key does) and `HistoryCipherFactory` says so; nothing derives it from a password or another secret.
- **Server:** nothing new, no field, no endpoint, no change to the protocol.
- **Cost:** `messages(group)` opens up to 1000 records through the bindings (200 on the web); the last-SENDING lookup is by reference so it stays out of that path.
- **Plan (each PR is high tier, `code-reviewer` and `security-reviewer`):** (1) the cipher, bindings, `:shared` interface, contract tests, ADR, threat model (merged); (2a) the `RecordStore` port, `EncryptedMessageStore`, the record codec and retention (merged); (2b) read marks persisted as sealed records (merged); (2c) the history key, its wrapping and the migration for existing identities (this stage); (2d) the sync engine: the `PendingSend` reference, the send order and reconciliation, and the receive failure behavior with its hard test; (3) the Android and web `RecordStore`s; (4) the app wiring, wipe, "reset history", the CLI command and the end-to-end step.
